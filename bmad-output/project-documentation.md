## 3. Entry Points and Key Flows

### Application Bootstrap

| Entry File | Role |
|------------|------|
| `packages/cli/src/bin.ts` | Entry point of the Bun-compiled standalone binary |
| `packages/cli/bin/reviewgate.mjs` | Entry point when run from a source/tsc checkout (used by the "install a launcher" path) |
| `packages/cli/src/index.ts` | Argument parsing and command dispatch (`open`, `serve`, `status`, `hook`, `update`) |
| `packages/server/src/app.ts` | Hono app construction — all `/api/*`, `/r/:id`, `/assets/*` routes |

### Primary Routing Layer

Hono app in `packages/server/src/app.ts`. Route groups:

- `GET /healthz` — liveness
- `POST /api/sessions` — create/attach a review session
- `GET /api/review/:id`, `GET /api/review/:id/files/:index`, `GET /api/review/:id/file` — review + diff data
- `POST/PATCH/DELETE /api/review/:id/comments[/:cid[/replies|/resolve]]` — comment CRUD, replies, resolve
- `PUT /api/review/:id/commit-message` — reviewer-edited commit message
- `POST /api/review/:id/chat` — chat with the read-only reviewer agent
- `POST /api/review/:id/pass` — trigger the automatic suggestion pass
- `POST /api/review/:id/suggestions/:sid/{accept,dismiss,reopen}` — suggestion lifecycle
- `POST /api/review/:id/decision` — the Approve / Request changes action (`ActionBar.tsx`'s target)
- `GET /api/review/:id/events` — Server-Sent Events stream (live updates to the web UI)
- `GET /r/:id` — serves the review's HTML shell
- `GET /assets/*`, `GET /favicon.svg` — static assets (the embedded web build)

### Authentication / Middleware Chain

Bearer token per review session (`ctx.token`, checked against the session), scoped to
`127.0.0.1` only — no external auth provider. No CORS/rate-limit middleware detected;
consistent with README's "everything runs on 127.0.0.1" design.

### Background Workers / Queues

None detected. The "automatic pass" (AI-generated suggestions) and chat both run as
on-demand async calls into the Claude Agent SDK, not a scheduled/queued job.

## 4. Module and Domain Structure

### Layer Breakdown

| Layer / Module | Path(s) | Inferred Responsibility |
|---------------|---------|------------------------|
| Domain model & persistence | `packages/core/src/review/` (`types.ts`, `store.ts`, `mutations.ts`, `approval.ts`, `anchor.ts`, `hash.ts`, `suggestions.ts`) | The `Review`/`Comment`/`Suggestion`/`Round` model; one JSON file per review under `.git/reviewgate/reviews/<id>.json` (outside version control); comment anchoring across diff rounds |
| Git integration | `packages/core/src/git/` (`GitClient.ts`, `NodeGitClient.ts`, `exec.ts`) | Abstraction over reading diffs/scopes from a real git repo |
| Diff processing | `packages/core/src/diff/` (`parse.ts`, `intraline.ts`) | Unified diff parsing and word-level (intraline) highlighting |
| PreToolUse hook | `packages/core/src/hook/` (`command.ts`, `feedback.ts`, `wait.ts`) + `packages/cli/src/commands/hook.ts` | Intercepts `git commit` Bash calls, blocks until a decision, formats the review's feedback back to Claude Code |
| HTTP API + AI reviewer | `packages/server/src/` (`app.ts`, `session.ts`, `agent.ts`, `highlight.ts`, `assets.ts`) | Serves the review API, the embedded web UI, SSE events, and the read-only agent-based reviewer |
| CLI commands | `packages/cli/src/commands/` (`open.ts`, `serve.ts`, `hook.ts`, `update.ts`) | User-facing `reviewgate` subcommands |
| Review UI | `packages/web/src/` (`App.tsx` + `components/`) | The browser UI: diff view, comments, chat, action bar |

### Cross-Cutting Utilities

- `packages/core/src/paths.ts`, `packages/core/src/types.ts`, `packages/core/src/version.ts` — shared types/paths/version constant, re-exported via `packages/core/src/index.ts` and a separate public `api.ts` surface (`@reviewgate/core/api`) consumed by the web package
- `packages/core/src/config.ts` — `.reviewgate.json` loader with defaults (see §5.6)
- `packages/web/src/lib/reviewClient.ts`, `rows.ts`, `code.ts` — API client + diff-row/code rendering helpers shared across web components

### Notable Domain Concepts (from naming)

`Review`, `Round` (one per commit attempt/re-review cycle), `Comment` (with `scope`:
`global`/`line`/`commit_message`, and `kind`: `issue`/`question`), `Suggestion` (AI-proposed,
`severity`: `blocker`/`consideration`/`nit`, can be promoted to a `Comment`), `Decision`
(`approve`/`request_changes`/`timeout`), `Anchor`/`anchorSnippet` (re-locating a comment's
line across diff rounds as code changes).

## 5. Conventions and Patterns

### Naming Conventions

| Artifact | Convention | Example |
|----------|-----------|---------|
| Files | camelCase for modules, PascalCase for React components | `mutations.ts`, `GitClient.ts`; `ActionBar.tsx` |
| Classes / Types | PascalCase | `NodeGitClient`, `ReviewGateConfig`, `Review` |
| Functions | camelCase, verb-first | `openComments`, `currentRound`, `cmdHook` |
| Constants | SCREAMING_SNAKE_CASE for module-level constants | `DEFAULT_CONFIG`, `MAX_TRANSCRIPT_CHARS`, `ALLOWED_TOOLS` |

### Module Resolution

Pure ESM throughout (`"type": "module"` in every package), explicit `.js` extensions in
relative imports (TS-with-ESM convention, e.g. `from "./commands/hook.js"`), workspace
packages referenced by name (`@reviewgate/core`, etc.) resolved via npm workspaces /
`tsc -b` project references. `packages/core` exposes two entry points: the default and
`@reviewgate/core/api` (a narrower surface for the web package).

### Concurrency Model

`async`/`await` throughout; no manual thread/worker pools. The PreToolUse hook is
deliberately synchronous-blocking from Claude Code's perspective (it waits on the human
decision) while the server itself is a normal async Node HTTP server.

### Error Handling Style

Custom typed error classes thrown and caught explicitly, e.g. `GitError` (`core`),
`UsageError` (`cli/src/args.ts`), `ClaudePathInvalid` (`server/src/claude-path.ts`). CLI
`main()` catches at the top level and maps errors to exit codes / stderr messages; no
global error-middleware framework, consistent with the small, single-purpose services here.

### Logging Approach

No structured logging library detected (no winston/pino/etc.). Output goes via direct
`process.stdout`/`process.stderr` writes in the CLI (e.g. `bin.ts`), and presumably
`console.*` elsewhere — matches a CLI-tool profile rather than a long-running logged service.

### Configuration and Secrets

`.reviewgate.json` in the repo root, parsed by `packages/core/src/config.ts`
(`ReviewGateConfig`): fully optional, defaults merged in (`DEFAULT_CONFIG`) — covers hook
timeout, ignored paths, auto-open/auto-review behavior, suggestion caps/dedupe thresholds,
theme. A couple of `REVIEWGATE_*` env vars are read directly in tests
(`REVIEWGATE_AUTO_REVIEW`, `REVIEWGATE_NO_OPEN`, per `vitest.config.ts`). No secrets
management detected — no API keys stored in this repo; the Claude Agent SDK call presumably
relies on the ambient Claude Code/CLI auth already on the machine (`claude-path.ts` resolves
the local `claude` CLI rather than embedding a key).

### Test File Location Convention

Co-located `*.test.ts` next to the source file it tests (e.g. `hash.ts` / `hash.test.ts`),
run by Vitest with `include: ["packages/*/src/**/*.test.ts"]`. Playwright specs live
separately under `e2e/*.spec.ts` with their own config and runner.

## 7. Planning Notes

_Observations from the scan that are relevant to planning but require a decision.
These are NOT implementation tasks — they are inputs for the PRD and architecture skills._

- The product's entire value proposition is the PreToolUse hook + human-decision gate
  (README: "A `deny` from a PreToolUse hook holds in *every* permission mode... The gate
  cannot be bypassed by the agent"). Any new feature should be evaluated against whether it
  weakens or preserves that guarantee.
- `packages/server/src/generated/web-assets.ts` is a generated file deliberately kept as a
  stub in git (per recent commit history: "build: put the generated asset file back to its
  stub") — planning/tooling work should be careful not to treat a locally-rebuilt version of
  this file as something to commit.
- There is an existing narrative design document, `plan.md` (43KB, referenced throughout the
  code as "§5", "§8", "§9", "§13" etc.), that appears to already function as an informal
  PRD/spec. Before writing a new PRD from scratch, it's worth deciding whether `bmad-prd`
  should treat `plan.md` as a primary input rather than starting cold.
- Comment/suggestion "anchoring" across diff rounds (`review/anchor.ts`, `anchorSnippet`) is
  a non-trivial piece of existing logic — new features touching comments or the diff view
  should account for how anchors are expected to survive re-review rounds.
- The web UI's "one action button that switches roles" pattern (`ActionBar.tsx`, and the
  recent full-screen decision message we just built) is a stated deliberate design choice
  ("§8" in code comments) — worth flagging explicitly to `bmad-prd`/`bmad-ux` as an existing
  UX principle to respect rather than relitigate.
