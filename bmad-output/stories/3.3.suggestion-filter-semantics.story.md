# 3.3: Filter tab behavior for suggestions (Open/All/Resolved/Outdated analogues)

**Story ID:** 3.3
**Epic:** 3 — Suggestions-in-Comments
**Slug:** suggestion-filter-semantics
**Status:** ready-for-dev

## Story

As a **reviewer**,
I want **the existing Open/All/Resolved/Outdated filter tabs to behave sensibly once suggestions are mixed into the list**,
so that **filtering the list stays meaningful instead of becoming confusing when two different status vocabularies (`CommentStatus` vs. `SuggestionStatus`) are shown together**.

## Acceptance Criteria

1. A decision is made and implemented for how `SuggestionStatus` (`pending`/`accepted`/`dismissed`) maps onto the existing `Filter` tabs (`open`/`all`/`resolved`/`outdated`); the mapping is documented in this story's Dev Agent Record or a code comment at the mapping site.
2. Under the "Open" filter, pending suggestions appear (as the analogue of an open comment); accepted suggestions do not appear as suggestions (they exist as real `Comment`s by then, per the existing `acceptSuggestion` flow, and are already counted there).
3. Under the "Resolved" filter, dismissed suggestions appear (as the analogue of a resolved comment) OR are excluded with a documented rationale — whichever choice is made, it must not silently hide suggestions with no way to see them at all in any tab.
4. Under "All", every suggestion appears regardless of status (matching "All"'s existing meaning for comments: no status filtering at all).
5. The filter tab counts (`counts.open`, `counts.all`, etc.) either include suggestions in their tallies with a documented rationale, or are scoped to comments-only with suggestions shown via a separate, clearly labeled count — whichever avoids a misleading number (e.g. "Open 3" must not silently mean "3 comments" when a 4th pending suggestion is also visible under that tab).

## Tasks / Subtasks

- [ ] Decide the status-mapping (Task 1 is a decision, not just code — write it down) (AC: #1)
- [ ] Implement the mapping inside the existing filter predicate (`groupComments`'s `kept = comments.filter(...)` equivalent, now operating on `ReviewRow[]`) (AC: #2, #3, #4)
- [ ] Update the `counts` computation (`CommentsPanel.tsx`'s `useMemo` building `{ open, all, resolved, outdated }`) to reflect the chosen approach from AC #5, keeping the numbers honest (AC: #5)
- [ ] Update the filter tab labels if the chosen approach benefits from a small label clarification (e.g. a tooltip or a secondary count) — optional, only if it measurably reduces ambiguity
- [ ] Add tests locking in the chosen mapping so a future change is deliberate, not accidental

## Dev Notes

- Today's filter predicate is purely comment-status based: `kept = comments.filter((c) => filter === "all" || c.status === filter)` (`CommentsPanel.tsx:184`), and `counts` tallies `c[comment.status] += 1` for every comment regardless of the active filter (`CommentsPanel.tsx:38-42`). Both need to become row-aware. [Source: packages/web/src/components/CommentsPanel.tsx]
- `SuggestionStatus` is `"pending" | "accepted" | "dismissed"` and has no `outdated` analogue at all — an "Outdated" filter tab naturally shows zero suggestions under any reasonable mapping, since nothing in `Suggestion` corresponds to a comment going stale across rounds (`Comment.status: "outdated"` exists because comments get re-anchored across review rounds; suggestions are closed outright via `closeOpenSuggestions` at decision time instead, per `session.ts`'s `decide()` — see "Open suggestions close with reason round_closed" comment there). [Source: packages/core/src/review/types.ts, packages/server/src/session.ts]
- Recommended mapping (record the final decision, override if a better read emerges during implementation): `pending` → treated as `open`; `dismissed` → treated as `resolved`; `accepted` suggestions are not shown as suggestion rows at all under any filter, since accepting a suggestion already produces a real `Comment` (via `promotedToCommentId`/`fromSuggestion` linkage) that is what should appear in the list from that point on — showing both would double-count the same feedback. [Inference — grounded in `Suggestion.promotedToCommentId`/`Comment.fromSuggestion` fields in packages/core/src/review/types.ts]
- On counts (AC #5): the simplest honest approach is to keep the four tab counts as comment-only counts (unchanged from today) and add a small, separately labeled suggestion count (e.g. "+2 suggestions") next to the relevant tab(s) — this avoids redefining what "Open 3" has always meant while still surfacing that suggestions exist. This is a judgment call, not a hard requirement from the tech-spec, which leaves the exact approach to be decided during implementation. [Source: tech-spec.md#fr-005-suggestions-appear-in-the-comments-list-must, Inference]
- Whatever mapping is chosen, FR-006's constraint is absolute: nothing here may change what feeds `openComments()`/the approval gate — that function operates on `review.comments` only and must not be touched by this story. [Source: tech-spec.md#fr-006-suggestions-in-the-list-never-affect-the-approverequest-changes-gate-must]

## Testing

- **Approach:** unit tests on the filter-predicate and counts logic (pure functions, per Story 3.1's extraction), plus a manual check of the tab UI reading naturally with mixed content.
- **Key scenarios:** a pending suggestion appears under "Open" and "All" but not "Resolved"/"Outdated"; a dismissed suggestion appears under "Resolved" and "All" but not "Open"/"Outdated"; an accepted suggestion appears nowhere as a suggestion row (its promoted `Comment` appears instead, under whatever filter that comment's own status matches); "Outdated" never shows a suggestion row.
- **Per-AC verification:** AC #1 → the mapping is present as a named function/table in code, reviewable in a diff; AC #2 → filter test for "Open" with pending suggestions present; AC #3 → filter test for "Resolved" with dismissed suggestions present; AC #4 → filter test for "All" showing every suggestion regardless of status; AC #5 → a test asserting the displayed counts match the chosen, documented rationale (comment-only counts + a separate suggestion indicator, or combined counts — whichever was implemented).
- **Fixtures / mocks:** extend Story 3.1/3.2's mixed fixtures with at least one suggestion in each status under each filter tab to exercise every combination.
- **Edge cases to cover:** a review with only accepted suggestions (list should look identical to a comments-only view, since accepted suggestions render as their promoted comments, not as suggestion rows); a review with suggestions but zero comments (the "No comments yet..." empty-state copy in `CommentsPanel.tsx` will need at least a check that it doesn't misleadingly claim there's nothing to see when suggestions are present).
