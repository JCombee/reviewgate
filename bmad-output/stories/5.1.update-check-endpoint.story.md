# 5.1: Relocate `latestTag`/`isNewer`; add cached `GET /api/update-check`

**Story ID:** 5.1
**Epic:** 5 — Update Checks
**Slug:** update-check-endpoint
**Status:** ready-for-dev

## Story

As the **ReviewGate server**,
I want **a `GET /api/update-check` endpoint that reuses the CLI's own GitHub-release-check logic and calls GitHub at most once per calendar day**,
so that **the web UI (Story 5.2) can learn a newer release exists without ReviewGate ever polling GitHub more than once a day**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `latestTag()`, `isNewer()`, and the `LatestTag` type are moved out of `packages/cli/src/commands/update.ts` into a module importable by both `cli` and `server` without a `server` → `cli` dependency (e.g. `packages/core/src/update.ts`, exported from `@reviewgate/core`); `packages/cli/src/commands/update.ts` imports them from `@reviewgate/core` instead of defining them locally, and `reviewgate update` / `reviewgate update --check` behave exactly as before the move.
2. `GET /api/update-check` returns `{ current: string; latest: string | null; updateAvailable: boolean }`, where `current` is the running server's version and `updateAvailable` is `true` only when `latest` is a non-null tag that `isNewer(latest, current)` reports as newer.
3. The first call to the endpoint on a given calendar day (local machine clock) calls GitHub's releases API (via `latestTag()`) at most once and writes the resulting verdict, tagged with that calendar day, to a cache file inside the server's existing local state directory (`stateDir(gitDir)`, `packages/server/src/lockfile.ts`).
4. Any subsequent call to the endpoint on the same calendar day returns the cached verdict without calling GitHub again; a call made on a later calendar day performs exactly one fresh GitHub call and overwrites the cache with the new day's verdict.
5. A failed GitHub check (network error, non-2xx status, timeout) resolves the endpoint to `{ latest: null, updateAvailable: false }` rather than throwing, hanging, or returning a 5xx — and that failed outcome is itself cached for the rest of the calendar day, so a failure does not trigger a retry on the next call that same day.
6. A missing, corrupt, or unparseable cache file is treated the same as "no check has run today yet" (a fresh check runs and a new cache file is written) rather than causing the endpoint to error.

[Source: bmad-output/epics.md#epic-5-update-checks]
- **Exact functions being relocated**, read directly from `packages/cli/src/commands/update.ts`:
  ```ts
  export interface LatestTag {
    tag: string | null;
    reason: "ok" | "none" | "unreachable";
  }

  export async function latestTag(): Promise<LatestTag> {
    try {
      const res = await fetch(`https://api.github.com/repos/${REPO}/releases/latest`, {
        headers: { accept: "application/vnd.github+json", "user-agent": "reviewgate" },
        signal: AbortSignal.timeout(10_000),
      });
      if (res.status === 404) return { tag: null, reason: "none" };
      if (!res.ok) return { tag: null, reason: "unreachable" };
      const body = (await res.json()) as { tag_name?: unknown };
      if (typeof body.tag_name !== "string") return { tag: null, reason: "none" };
      return { tag: body.tag_name, reason: "ok" };
    } catch {
      return { tag: null, reason: "unreachable" };
    }
  }

  export function isNewer(candidate: string, current: string): boolean {
    const parts = (v: string) =>
      v.replace(/^v/, "").split("-")[0]!.split(".").map((n) => Number.parseInt(n, 10) || 0);
    const a = parts(candidate);
    const b = parts(current);
    for (let i = 0; i < Math.max(a.length, b.length); i++) {
      const x = a[i] ?? 0;
      const y = b[i] ?? 0;
      if (x !== y) return x > y;
    }
    return false;
  }
  ```
  `REPO`/`VERSION` are already exported from `@reviewgate/core` (`packages/core/src/version.ts`) — only `latestTag`/`isNewer`/`LatestTag` need to move; `assetName`, `binaryPath`, `download`, `assetSource`, `findReleaseByTag`, `replaceSelf`, `sweepOldBinary` are CLI-self-update-specific and stay in `packages/cli/src/commands/update.ts` unchanged. [Source: packages/cli/src/commands/update.ts]
- **Existing state-file convention to mirror**, read directly from `packages/server/src/lockfile.ts`: `stateDir(gitDir)` returns `path.join(gitDir, "reviewgate")`; `writeServerRecord` does `fs.mkdir(dir, { recursive: true })` then an atomic `writeFile` to a `.${pid}.tmp` path followed by `fs.rename` to the final path; `readServerRecord` wraps `JSON.parse` + a `isServerRecord` shape guard in a try/catch that returns `null` on any failure (missing file, bad JSON, wrong shape) rather than throwing. The new update-check cache file should follow the exact same shape-validated, atomic-write pattern, living in the same `stateDir(gitDir)` directory (a new filename, e.g. `update-check.json`, sitting next to the existing `server.json`). [Source: packages/server/src/lockfile.ts]
- **`AppDeps` currently has no `gitDir`.** `packages/server/src/app.ts`'s `AppDeps` interface only carries `serverToken`, `repoRoot`, `version`; `createApp` is called once in production, from `startServer` in `packages/server/src/index.ts`, which already has `info.gitDir` in scope (`const info = await git.info()`, the same `info` object `info.root` is drawn from for `repoRoot`) — add `gitDir: info.gitDir` to that call's `AppDeps` literal. The only other call site is the integration test harness in `packages/server/src/app.test.ts`, which constructs `createApp({ serverToken, repoRoot: repo.root, version: "test" }, store)` and will need a `gitDir` value too (a `TestRepo` only exposes `root`; for a freshly `git init`'d repo with no separate worktree, `path.join(repo.root, ".git")` is the real `.git` directory). [Source: packages/server/src/app.ts]; [Source: packages/server/src/index.ts]; [Source: packages/server/src/app.test.ts]; [Source: packages/core/src/git/testRepo.ts]
- **Shared response type convention:** `packages/core/src/api.ts` already holds every server/web-shared API response shape (`ReviewSummary`, `FileDetail`, `PassStatus`, `ReviewEvent`, `ApiError`, etc.), imported by both `packages/server` (implicitly, via matching response shapes) and `packages/web` (`import type { ... } from "@reviewgate/core/api"` in `App.tsx`/`reviewClient.ts`). The new `{ current, latest, updateAvailable }` contract belongs there too, as `UpdateCheckResult`, so Story 5.2's web code can import the same type the server route returns rather than redeclaring it. [Source: packages/core/src/api.ts]
- **Route registration pattern to follow**, read directly from `packages/server/src/app.ts`: unauthenticated, non-review-scoped routes (`/healthz`) are registered directly on `app` with no `resolve(c)`/token check, unlike every `/api/review/:id/...` route which calls `resolve(c)` and checks the per-review token. `GET /api/update-check` is not tied to any review and carries no review token, so it should follow the `/healthz` pattern: registered near the top of `createApp`, no auth check, reading only from `deps` (mirroring `/healthz`'s `c.json({ ok: true, version: deps.version, repoRoot: deps.repoRoot, sessions: store.size })`). [Inference — the tech spec's route contract does not state an auth requirement, and `project-context.md`'s "everything runs locally on 127.0.0.1, no accounts" constraint plus the existing unauthenticated `/healthz` precedent make an unauthenticated route the consistent choice; there is no per-review or per-server secret this endpoint would need to protect, since it echoes only the public GitHub releases API's own answer]. [Source: packages/server/src/app.ts]; [Source: bmad-output/project-context.md#core-constraints]
- **"Calendar day" means the local machine's clock, not UTC.** [Source: tech-spec.md#assumptions] states: "'daily' means once per calendar day on the local machine's clock — no requirement for a precise 24h rolling window or cross-machine coordination." `Date.prototype.toISOString()` reports the UTC date, which can differ from the local calendar day near midnight in any timezone away from UTC+0 — the day-stamp must be computed from local `Date` getters (`getFullYear()`/`getMonth()`/`getDate()`), not `toISOString().slice(0, 10)`. [Inference — the tech spec states the "local machine clock" requirement but does not spell out the exact date-formatting call; this is the concrete implication of that requirement for whoever writes the day-stamp comparison]
- **Failure caching is explicit in the requirement, not incidental:** FR-008's own acceptance criteria state a failed check "does not retry more than once per day" — this means the cache must be written even when `latestTag()` returns `reason: "unreachable"` or `"none"` (i.e. `tag: null`), with `latest: null` and `updateAvailable: false`, so a second call the same day still reads the cache instead of hitting GitHub again. [Source: tech-spec.md#fr-008-daily-cached-update-check-with-an-in-app-prompt-must]
- **Malformed cache handling mirrors an existing pattern in this codebase:** the Risks table entry "Update-check cache file format changes later and an old cached file with a stale schema causes a crash instead of a fresh check" is mitigated by treating any unparseable/unexpected cache file the same as "no cache" (re-check), "mirroring `loadConfig`'s 'malformed input → default' pattern" — the same defensive posture `readServerRecord` already uses (try/catch + shape guard returning `null`). [Source: tech-spec.md#risks--mitigations]
- **Never blocks the hook/commit path:** "the update check must never block hook/commit flow — it is purely a web-UI concern, called from the browser, not from the PreToolUse hook path." This route must not be called from, or awaited by, `packages/cli/src/commands/hook.ts`'s `decide()` — it is reachable only via the browser's `fetch` against the running review server. [Source: tech-spec.md#constraints]
- **No new telemetry:** "the update check (FR-008) only ever reads the public GitHub releases API (same endpoint the CLI already calls) and never sends anything beyond the request itself — no telemetry, no machine identifiers." Do not add a machine id, hostname, or any other identifying value to the GitHub request beyond what `latestTag()` already sends (`accept`/`user-agent: reviewgate` headers). [Source: tech-spec.md#security]
- **Out of scope reminders:** no auto-install of the update (that is Story 5.2's modal, which only shows the command); no change to `reviewgate update`'s own CLI behavior beyond the relocation itself. [Source: bmad-output/epics.md#epic-5-update-checks]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Approach:** unit-test the pure/deterministic pieces (`isNewer`'s existing coverage, now relocated; the caching wrapper's date-comparison branches) in isolation from real network access, then add one integration test at the HTTP layer (`app.fetch`, the same pattern `app.test.ts` already uses for every other route) to prove the endpoint contract and the once-per-day behavior end to end. [Source: tech-spec.md#unit-testing-focus]
- **Key scenarios:**
  - `isNewer()`'s existing test cases (numeric vs. lexicographic comparison, missing `v` prefix, equal versions, a source build always behind) continue to pass unchanged after the move to `packages/core/src/update.test.ts` (AC #1).
  - `checkForUpdate(gitDir, current)` with no cache file present: calls the injected/mocked `latestTag()` exactly once, writes a cache file dated today, and returns a result consistent with the mocked tag and `isNewer()` (AC #2, #3).
  - `checkForUpdate(gitDir, current)` with a cache file dated today already present: does not call `latestTag()` again and returns the cached verdict verbatim (AC #4).
  - `checkForUpdate(gitDir, current)` with a cache file dated a prior calendar day: calls `latestTag()` again and overwrites the cache with the new day's verdict (AC #4).
  - `checkForUpdate(gitDir, current)` when the mocked `latestTag()` resolves to `{ tag: null, reason: "unreachable" }`: returns `{ latest: null, updateAvailable: false }` and still writes a cache entry for today, so a second call the same day makes no further GitHub call (AC #5).
  - A cache file containing invalid JSON, or valid JSON missing the expected fields, is treated as absent: a fresh check runs and a new, well-formed cache file is written (AC #6).
  - Integration: `GET /api/update-check` against the test app returns the documented `{ current, latest, updateAvailable }` shape; calling it twice back-to-back triggers only one underlying GitHub call; after the test forces the cache's stored date backward by one day, a third call triggers exactly one more GitHub call (per tech-spec's Round 2 integration scenario) (AC #2, #3, #4).
- **Fixtures/mocks:** this codebase has no existing convention for mocking `fetch`/network calls in tests (`update.test.ts` today only exercises the pure `isNewer`/`assetName` functions, never `latestTag()` itself, precisely because it hits real network) — the caching wrapper should be written so its test can substitute a fake "latest tag" lookup (e.g. accepting the lookup function as a parameter, or mocking `@reviewgate/core`'s `latestTag` export via `vi.mock` with `importOriginal` for the rest of the module) rather than hitting `api.github.com` from the test suite. Use a real temporary `TestRepo`-backed `gitDir` for the cache-file read/write tests, consistent with how `app.test.ts` already uses `TestRepo` for filesystem-backed integration tests. [Source: packages/cli/src/commands/update.test.ts]; [Source: packages/server/src/app.test.ts]
- **Edge cases to cover:** the exact midnight-local-time boundary (a cache dated "yesterday" by local-day comparison must trigger a fresh check even though less than 24 wall-clock hours may have passed, and vice versa — this is a calendar-day rule, not a rolling-window one, per the Assumptions citation above); a `stateDir(gitDir)` directory that does not yet exist on first run (must be created, mirroring `writeServerRecord`'s `fs.mkdir(..., { recursive: true })`); concurrent calls to the endpoint within the same brief window before any cache file exists (acceptable to make more than one GitHub call in that narrow race — the tech spec's "once per calendar day" guarantee is a steady-state property, not a mutual-exclusion lock, and no story or requirement calls for one).
