# 1.4: Web chat switcher UI in `ChatPanel.tsx`/`App.tsx`

**Story ID:** 1.4
**Epic:** 1 — Multiple Chats
**Slug:** chat-switcher-ui
**Status:** done

## Story

As a **reviewer**,
I want **to see all my chats for this review, switch between them, and start a new one from the panel**,
so that **I can hold more than one conversation with the assistant without them mixing together**.

## Acceptance Criteria

1. `ChatPanel.tsx` renders a list/tabs of `review.chats`, each showing at least a title and its message count; the currently active chat is visually indicated.
2. Clicking a chat in the list makes it the active chat: its `messages` render below, and sending a message calls `api.chat(activeChatId, message)`.
3. A "New chat" control calls `api.createChat()` and the newly created chat becomes the active chat once it appears in `review.chats`.
4. `App.tsx`'s `streaming` state is keyed by chat id (e.g. `Record<string, string>`) so tokens streamed for one chat never appear under another chat, including when the reviewer switches chats mid-stream.
5. The existing "Ask the author" comment-conversion action and the `PassIndicator`/read-only footer continue to work exactly as before, scoped to whichever chat is active.

## Tasks / Subtasks

- [ ] Add `activeChatId` state to `App.tsx` (default: first chat in `review.chats`, or none if empty) (AC: #2)
- [ ] Change `App.tsx`'s `streaming: string | null` to a per-chat-id map; update the `onChatToken` handler (now `(chatId, text)`) to append into `streaming[chatId]` (AC: #4)
- [ ] Pass `chats`, `activeChatId`, `onSelectChat`, `onNewChat` into `ChatPanel.tsx`; render the switcher UI above the message thread (AC: #1, #2, #3)
- [ ] Update `ChatPanel.tsx`'s `send()` to call `api.chat(activeChatId, message)` instead of `api.chat(message)` (AC: #2)
- [ ] Wire "New chat" to `api.createChat()` and auto-select the resulting chat once `review.chats` updates (AC: #3)
- [ ] Confirm `PassIndicator`, the "Ask the author" button, and the read-only footer still render/behave correctly against the active chat only (AC: #5)
- [ ] Manually verify in the browser: two chats, switch mid-stream, confirm no token cross-talk

## Dev Notes

- `ChatPanel.tsx` today takes `{ ctx, review, api, streaming, passStatus, draft, onDraftUsed }`, renders `review.chat.map(...)` as one flat list, and its `send()` calls `api.chat(message)`. [Source: packages/web/src/components/ChatPanel.tsx]
- `App.tsx` currently owns one `const [streaming, setStreaming] = useState<string | null>(null)` and one `onChatToken: (text) => setStreaming((prev) => (prev ?? "") + text)`; `onReview` resets `streaming` to `null` whenever a fresh `Review` arrives over SSE (because the answer has landed in the review itself by then). Keying `streaming` by chat id means the reset on `onReview` should clear only the chat id(s) whose messages just landed, or simply clear the whole map — clearing the whole map is simpler and matches today's "streaming state is transient, the review is authoritative" behavior. [Source: packages/web/src/App.tsx]
- `PanelTab`/`panelOpen` state (chat vs. comments tab, `App.tsx`) is unrelated to the chat switcher inside the chat tab — do not conflate the two. The chat switcher is a new UI element *inside* the existing "chat" panel tab. [Source: packages/web/src/App.tsx]
- The `chatDraft`/`onDraftUsed` mechanism (used by `Overview.tsx`'s "Discuss" action on a suggestion, per `App.tsx`'s `onDiscuss` wiring) should populate the draft into whichever chat is currently active; if no chat exists yet, "Discuss" should trigger `onNewChat()` first so there is always a chat to receive the draft. [Inference]
- `api.chat`/`api.createChat` come from Story 1.3's updated `ReviewApi` interface (`chat(chatId, message)`, `createChat(title?, model?)`) — this story only consumes that interface, it does not change `reviewClient.ts`. [Source: bmad-output/stories/1.3.chat-api-routes.story.md]
- Keep the switcher visually minimal, consistent with the panel's existing terse, low-chrome style (see `CommentsPanel.tsx`'s filter-tab row for a precedent: small bordered buttons with `aria-pressed`). [Source: packages/web/src/components/CommentsPanel.tsx]

## Testing

- **Approach:** component-level tests (if the web package has a test setup for React components) plus a manual browser verification pass, since this story is UI-heavy and SSE-timing-sensitive.
- **Key scenarios:** switching chats shows the right message history; sending a message in chat A while chat B is active does not append to chat B; creating a new chat selects it automatically; the read-only footer and "Ask the author" button still work against whichever chat is active.
- **Per-AC verification:** AC #1 → render test/manual check that all `review.chats` appear with title + count; AC #2 → manual/interaction test that clicking a chat then sending a message posts with that chat's id; AC #3 → manual test that "New chat" results in an empty active thread; AC #4 → manual two-chat mid-stream-switch test (open chat A, send a question, immediately switch to chat B before the answer completes, switch back to A and confirm the full answer is there and B never showed A's tokens); AC #5 → manual regression check of "Ask the author" and the pass indicator.
- **Fixtures / mocks:** a `Review` fixture with two or more `chats`, one with an in-progress stream simulated via a mocked SSE token sequence.
- **Edge cases to cover:** a review with zero chats (empty state — show only "New chat"); a review just migrated from the legacy single-chat shape (exactly one chat, no switcher clutter needed for one chat, though the switcher UI itself can simply render one item without special-casing).

## Learnings from Previous Stories

- From 1.3: `ReviewApi.chat` is now `(chatId, message)` and `ReviewApi.createChat(title?, model?)` exists; `onChatToken` is now `(chatId, text)`. This story is the first consumer of both changes.
- From 1.1/1.2: a freshly migrated legacy review always has exactly one `Chat` in `review.chats` — the switcher must handle the one-chat case gracefully as the common case, not just the multi-chat case.

## Dev Agent Record

**Implementation summary:**

- `packages/web/src/components/ChatPanel.tsx`: reworked to take `chats: Chat[]`, `activeChatId: string | null`, `onSelectChat`, `onNewChat` instead of `review: Review` (the component only ever used `review.chat`, so the narrower props replace it cleanly). Added a switcher row (`role="tablist"`, one `role="tab"` button per chat showing `title` + `messages.length`, `aria-pressed` on the active one, styled after `CommentsPanel.tsx`'s filter-tab row) above the message thread, plus a "+ New chat" button. `send()` now calls `api.chat(activeChatId, message)` and is a no-op when `activeChatId` is null (AC #1, #2, #3).
- Empty state: when `chats.length === 0` the switcher row still renders (with only "+ New chat"), and the thread/input area is replaced with a short "No conversation yet. Start one with 'New chat'." message — no textarea/Ask/Ask-the-author controls are shown until a chat exists, per the Testing section's "show only 'New chat'" edge case.
- The "Discuss" draft effect now triggers `onNewChat()` first if `activeChatId` is null before populating the draft into the (local, persistent) `text` state — so a suggestion's "Discuss" action always has somewhere to land even on a review with zero chats (Dev Notes' inference item).
- `PassIndicator` and "Ask the author" are unchanged in behavior; both are scoped to the active chat implicitly (the former doesn't depend on chat, the latter posts a comment independent of chat) (AC #5).
- `packages/web/src/App.tsx`: `streaming` is now `Record<string, string>` (was `string | null`); `onChatToken(chatId, text)` merges into `streaming[chatId]`; `onReview` clears the whole map (matches the Dev Notes' "clearing the whole map is simpler" guidance, since the answer has landed in the review itself by then). Added `activeChatId` state plus a `useEffect` keyed on `review` that: on first load, defaults to `review.chats[0]?.id`; on every later update, diffs the current chat ids against a `knownChatIdsRef` set and auto-selects the newest id that wasn't known before (covers both "New chat" clicks and the "Discuss" auto-created chat); otherwise keeps the current `activeChatId` if it still exists, or falls back to the first chat if it was removed. `ChatPanel` is now called with `chats={review.chats}`, `activeChatId`, `onSelectChat={setActiveChatId}`, `onNewChat={() => void api.createChat()}`, and `streaming={activeChatId !== null ? (streaming[activeChatId] ?? null) : null}` (AC #2, #3, #4).

**Judgment calls / notes for the record:**

- **No React component test harness exists** in `packages/web` (no jsdom/testing-library dependency, no `*.test.tsx` files, no test `environment` configured in the vite/vitest setup — only plain-function tests in `lib/*.test.ts`). The Testing section's own approach line anticipates this ("component-level tests (if the web package has a test setup for React components) plus a manual browser verification pass"). Since setting up a React testing stack is not part of this story's Owned File/Module Scope (only `ChatPanel.tsx` and `App.tsx`) and would be a much larger, separate infrastructure change, no component tests were added. In its place: (1) `npx tsc --noEmit` on `packages/web` is clean, (2) `npm run build:web` (a real Vite production build) succeeds, (3) the full `npm test` (263/263) shows no regressions elsewhere, and (4) I traced the acceptance criteria against the code by hand (see below) in place of an interactive browser session, which was not available in this environment either. Flagging this as a real gap: nobody has clicked through this UI in a live browser. Worth a manual pass before shipping.
- **AC #1 (list/tabs with title + count, active indicated):** satisfied by the new switcher row — each button shows `c.title` and `c.messages.length`, and `aria-pressed`/background-color distinguish the active one.
- **AC #2 (click switches, send scopes to it):** `onSelectChat` is wired directly to `setActiveChatId`; `send()` reads `activeChatId` at call time and passes it to `api.chat`.
- **AC #3 (New chat creates and activates):** `onNewChat` calls `api.createChat()` (fire-and-forget, matching the pattern of every other mutating call in this codebase, e.g. `restartPass`); the resulting `Review` arrives over the same SSE `onReview` path as any other mutation, and the `activeChatId`-tracking effect in `App.tsx` detects the new chat id (not in `knownChatIdsRef`) and selects it automatically. This also transparently covers the "Discuss" auto-created-chat case using the same code path, since both go through `review.chats` changing.
- **AC #4 (streaming keyed by chat id):** verified by construction — `streaming` is a `Record<string, string>` keyed by the `chatId` argument SSE hands `onChatToken`, and `ChatPanel` only ever receives the slice for `activeChatId`. Switching `activeChatId` mid-stream simply changes which slice `ChatPanel` is given; the other chat's accumulating entry in the map is untouched and reappears correctly if the user switches back before the next `onReview` clears the map.
- **AC #5 (PassIndicator / Ask the author unaffected):** neither reads or writes anything chat-scoped; both continued to render in the same top-bar/footer position, now simply inside the "there is an active chat" branch of the component (Ask the author) or unconditionally (PassIndicator, top bar).
- Left `ctx` as an unused destructured prop on `ChatPanel` — it was already unused in the pre-existing component (dead prop, not introduced by this change) and removing it was out of scope.
- Did not touch `reviewClient.ts`, `Overview.tsx`, `CommentsPanel.tsx`, or any other file — only `ChatPanel.tsx` and `App.tsx`, per Owned File/Module Scope.
