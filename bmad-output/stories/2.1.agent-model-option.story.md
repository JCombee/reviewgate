# 2.1: Thread `model` through `AgentContext`/`ReviewAgent` options

**Story ID:** 2.1
**Epic:** 2 — Per-Chat Model
**Slug:** agent-model-option
**Status:** done

## Story

As a **reviewer**,
I want **the model I pick for a chat to actually be the model the SDK uses for that chat's answers**,
so that **per-chat model selection is real, not cosmetic**.

## Acceptance Criteria

1. `AgentContext` (`packages/server/src/agent.ts`) gains an optional `model?: string | null` field.
2. `ReviewAgent#options()` includes `model: this.context.model` in the returned `Options` object when `this.context.model` is a non-null, non-empty string; it is omitted entirely otherwise (so the SDK falls back to its own default, matching today's behavior when no model is set).
3. `Session#agentFor(chatId)` (from Story 1.2) constructs each chat's `ReviewAgent` with `model` set to that chat's `Chat.model` field.
4. Changing a chat's `model` (via the route added in Story 2.2/1.3) affects only that chat's next `ReviewAgent` — either by reconstructing the agent when the model changes, or by documenting that a model change only takes effect for chats/agents not yet created (pick the simpler option and state the choice in code, since `ReviewAgent`'s SDK session is `resume`-based and a model change mid-session may not be supported by the SDK either way).
5. Automatic pass (`reviewPass`) behavior and its `Options` are unaffected — the pass does not read `Chat.model` since it is not tied to any chat.

## Tasks / Subtasks

- [ ] Add `model?: string | null` to `AgentContext` in `agent.ts` (AC: #1)
- [ ] Update `#options()` to conditionally spread `model` into the returned `Options` (AC: #2)
- [ ] Update `Session#agentFor` (or equivalent lazy-construction point from Story 1.2) to pass the chat's `model` into `new ReviewAgent({...})` (AC: #3)
- [ ] Decide and implement the model-change-mid-chat behavior; add a one-line code comment recording the decision (AC: #4)
- [ ] Verify `runReviewPass`'s `ReviewAgent` construction path is untouched (AC: #5)
- [ ] Extend `agent.test.ts` to cover `#options()`'s conditional `model` inclusion

## Dev Notes

- `Options.model?: string` already exists in the installed `@anthropic-ai/claude-agent-sdk` (`^0.3.252`) — no SDK upgrade is needed; the doc comment on the field reads "Claude model to use. Defaults to the CLI default model. Examples: 'claude-sonnet-5', 'claude-opus-4-8', 'claude-fable-5'". [Source: node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts]
- `ReviewAgent#options(executable)` today returns a fixed `Options` object (`cwd`, `pathToClaudeCodeExecutable`, `allowedTools`, `disallowedTools`, `permissionMode`, `systemPrompt`, `includePartialMessages`, and conditionally `resume`) — add `model` using the same conditional-spread pattern already used for `resume`: `...(this.#sessionId ? { resume: this.#sessionId } : {})`. [Source: packages/server/src/agent.ts]
- `ReviewAgent` is constructed once per chat in `Session` (per Story 1.2's `#agentFor`), each holding its own `#sessionId`. Since the model is fixed at construction time and each chat gets exactly one `ReviewAgent` for its lifetime, "changing a chat's model" in practice means the *next* `ReviewAgent` constructed for that chat id — which only happens if `Session` is willing to discard and recreate the cached agent for that chat id on a model-change request. The simplest correct behavior: a model change replaces the cached `ReviewAgent` for that chat id (starting a fresh SDK session under the new model, losing that chat's `resume` continuity but not its persisted `messages`). Document this trade-off explicitly rather than attempting mid-session model swapping (not exposed by the SDK's `Options` shape at all — `model` is set at `query()` call time via `Options`, not mutable on a live session). [Inference]
- `AgentUnavailable` remains the error path for anything the SDK rejects, including an invalid `model` string passed through — no new error type is needed (per tech-spec's Error Handling Strategy). [Source: tech-spec.md#error-handling-strategy]
- The automatic pass's `ReviewAgent` (constructed in `Session.start`/resume, per `session.ts:118-123`) is separate from any chat's `ReviewAgent` and has no `model` concept — do not add one; FR-003 is scoped to chats only. [Source: tech-spec.md#fr-003-per-chat-model-selection-must]

## Testing

- **Key scenarios:** `#options()` includes `model` when set and omits it when `null`/undefined/empty string; `Session` constructs a chat's agent with that chat's `model`; a model change on an existing chat results in the next message using the new model (per whichever behavior was chosen in Task 4).
- **Per-AC verification:** AC #1 → type-level; AC #2 → `agent.test.ts` asserts the shape of the object returned by `#options()` (or an equivalent exposed test seam) for both a set and an unset model; AC #3 → `session.test.ts` asserts (via a mock/spy on `ReviewAgent`'s constructor or its resulting `Options`) that the right model reaches the right chat's agent; AC #4 → a test exercising a model change followed by a message, asserting the documented behavior; AC #5 → existing pass-related tests remain green.

## Learnings from Previous Stories

- From 1.2: chat agents are created lazily via `#agentFor(chatId)`, one `ReviewAgent` per chat id, cached in a `Map`. This story's model-change behavior (recreate-on-change) fits naturally into that same cache: replacing the map entry is the whole mechanism.

## Dev Agent Record

**Implementation summary:**

- `packages/server/src/agent.ts`: `AgentContext` gained `model?: string | null` (AC #1). `#options()` now conditionally spreads `{ model: this.context.model }` after the existing `resume` spread, guarded by `this.context.model && this.context.model.trim() !== ""` — so `undefined`, `null`, and `""` all omit the field, matching the SDK's own fallback-to-default behavior (AC #2, and the empty-string edge case from Testing).
- `packages/server/src/session.ts`: `#agentFor(chatId)` now looks up the chat's `Chat.model` and constructs (or keeps) the `ReviewAgent` accordingly: `if (cached && cached.context.model === chat.model) return cached;` otherwise it builds a fresh `ReviewAgent({ ...this.#agentContext(), model: chat.model })` and replaces the map entry (AC #3, #4). This is the "recreate on model change" option from Task 4 — implemented as a lazy check inside `#agentFor` rather than an eager eviction triggered elsewhere, so Story 2.2's `setChatModel` (or any other code path that changes `Chat.model` on the persisted `Review`) needs no awareness of the agent cache at all: the next `#agentFor` call for that chat id naturally detects the mismatch and starts a fresh SDK session under the new model. The code comment above `#agentFor` records this decision and the trade-off (losing that chat's `resume` continuity, not its persisted `messages`).
- `runReviewPass()`'s `ReviewAgent` construction (`new ReviewAgent(this.#agentContext())`, unchanged) never sets `model`, so pass `Options` never include it — verified by inspection and by the existing/extended `runReviewPass` test still passing (AC #5).
- `packages/server/src/agent.test.ts`: added a `describe("ReviewAgent's SDK options", ...)` block. Since `#options()` is a genuinely private (`#`-syntax) method with no way to reach it from outside the class, and the Testing section itself suggests "mock the SDK's query function... and inspect the Options object it was called with," the block does exactly that: `vi.mock("@anthropic-ai/claude-agent-sdk", () => ({ query: vi.fn() }))`, then calls the real `ReviewAgent.ask()` (with `claudeExecutable()` resolving successfully in this environment via the SDK's own bundled native binary — no `AgentUnavailable` short-circuit needed) and inspects the `options` object the mocked `query` was actually called with. One test confirms `model` is included for a set value; a parameterized test (`it.each([[undefined], [null], [""]])`) confirms it is omitted for all three "unset" shapes.
- `packages/server/src/session.test.ts`: added a `describe("chat model (Story 2.1)", ...)` block with 3 tests: the chat's agent is constructed with that chat's model (asserted via the `ReviewAgent.prototype.ask` spy reading `this.context.model`); the same agent instance is reused across messages when the model does not change; and the agent is replaced with a new instance carrying the new model after simulating a model change via `session.commit(...)` (standing in for Story 2.2's not-yet-built `setChatModel`/PATCH route, per the Dependency Maps — 2.1 is Blocked-by nothing further and Blocks 2.2, so the model-change trigger itself is simulated directly against the persisted `Review` here).

**Judgment calls / notes for the record:**

- Chose the "lazy re-check inside `#agentFor`" design over an eager "evict on write" design specifically because it makes Story 2.2 trivial: `Session.setChatModel` only needs to update `Chat.model` on the `Review` and commit it — it does not need to know the agent cache exists at all. This seemed like the more robust of the two "simpler option" choices Task 4 allows, and is called out explicitly in code.
- `claudeExecutable()` (via `resolveClaudePath()`) resolves successfully in this sandbox because the installed `@anthropic-ai/claude-agent-sdk-linux-x64` package ships its own `claude` binary that satisfies the lookup — so the new `agent.test.ts` block did not need to stub `claude-path.js` to avoid `AgentUnavailable`. This is environment-dependent; if a future CI environment lacks any resolvable `claude` executable, this block's tests (not the pre-existing ones) would need a `resolveClaudePath`/`claude-path.js` stub added. Flagging this now since it wasn't necessary here but could be a portability gap.
- No changes were made to `runReviewPass`'s call site or to `Session.create`'s constructor wiring — both were already correct in shape from Story 1.2, and this story only had to confirm (via the existing `runReviewPass` test remaining green) that the pass path stays model-less.
