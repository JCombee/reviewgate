# 2.1: Thread `model` through `AgentContext`/`ReviewAgent` options

**Story ID:** 2.1
**Epic:** 2 — Per-Chat Model
**Slug:** agent-model-option
**Status:** ready-for-dev

## Story

As a **reviewer**,
I want **the model I pick for a chat to actually be the model the SDK uses for that chat's answers**,
so that **per-chat model selection is real, not cosmetic**.

## Acceptance Criteria

1. `AgentContext` (`packages/server/src/agent.ts`) gains an optional `model?: string | null` field.
2. `ReviewAgent#options()` includes `model: this.context.model` in the returned `Options` object when `this.context.model` is a non-null, non-empty string; it is omitted entirely otherwise (so the SDK falls back to its own default, matching today's behavior when no model is set).
3. `Session#agentFor(chatId)` (from Story 1.2) constructs each chat's `ReviewAgent` with `model` set to that chat's `Chat.model` field.
4. Changing a chat's `model` (via the route added in Story 2.2/1.3) affects only that chat's next `ReviewAgent` — either by reconstructing the agent when the model changes, or by documenting that a model change only takes effect for chats/agents not yet created (pick the simpler option and state the choice in code, since `ReviewAgent`'s SDK session is `resume`-based and a model change mid-session may not be supported by the SDK either way).
5. Automatic pass (`reviewPass`) behavior and its `Options` are unaffected — the pass does not read `Chat.model` since it is not tied to any chat.

## Tasks / Subtasks

- [ ] Add `model?: string | null` to `AgentContext` in `agent.ts` (AC: #1)
- [ ] Update `#options()` to conditionally spread `model` into the returned `Options` (AC: #2)
- [ ] Update `Session#agentFor` (or equivalent lazy-construction point from Story 1.2) to pass the chat's `model` into `new ReviewAgent({...})` (AC: #3)
- [ ] Decide and implement the model-change-mid-chat behavior; add a one-line code comment recording the decision (AC: #4)
- [ ] Verify `runReviewPass`'s `ReviewAgent` construction path is untouched (AC: #5)

## Dev Notes

- `Options.model?: string` already exists in the installed `@anthropic-ai/claude-agent-sdk` (`^0.3.252`) — no SDK upgrade is needed; the doc comment on the field reads "Claude model to use. Defaults to the CLI default model. Examples: 'claude-sonnet-5', 'claude-opus-4-8', 'claude-fable-5'". [Source: node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts]
- `ReviewAgent#options(executable)` today returns a fixed `Options` object (`cwd`, `pathToClaudeCodeExecutable`, `allowedTools`, `disallowedTools`, `permissionMode`, `systemPrompt`, `includePartialMessages`, and conditionally `resume`) — add `model` using the same conditional-spread pattern already used for `resume`: `...(this.#sessionId ? { resume: this.#sessionId } : {})`. [Source: packages/server/src/agent.ts]
- `ReviewAgent` is constructed once per chat in `Session` (per Story 1.2's `#agentFor`), each holding its own `#sessionId`. Since the model is fixed at construction time and each chat gets exactly one `ReviewAgent` for its lifetime, "changing a chat's model" in practice means the *next* `ReviewAgent` constructed for that chat id — which only happens if `Session` is willing to discard and recreate the cached agent for that chat id on a model-change request. The simplest correct behavior: a model change replaces the cached `ReviewAgent` for that chat id (starting a fresh SDK session under the new model, losing that chat's `resume` continuity but not its persisted `messages`). Document this trade-off explicitly rather than attempting mid-session model swapping (not exposed by the SDK's `Options` shape at all — `model` is set at `query()` call time via `Options`, not mutable on a live session). [Inference]
- `AgentUnavailable` remains the error path for anything the SDK rejects, including an invalid `model` string passed through — no new error type is needed (per tech-spec's Error Handling Strategy). [Source: tech-spec.md#error-handling-strategy]
- The automatic pass's `ReviewAgent` (constructed in `Session.start`/resume, per `session.ts:118-123`) is separate from any chat's `ReviewAgent` and has no `model` concept — do not add one; FR-003 is scoped to chats only. [Source: tech-spec.md#fr-003-per-chat-model-selection-must]

## Testing

- **Approach:** unit tests in `packages/server/src/agent.test.ts` (existing file) and `packages/server/src/session.test.ts` (added in Story 1.2).
- **Key scenarios:** `#options()` includes `model` when set and omits it when `null`/undefined/empty string; `Session` constructs a chat's agent with that chat's `model`; a model change on an existing chat results in the next message using the new model (per whichever behavior was chosen in Task 4).
- **Per-AC verification:** AC #1 → type-level; AC #2 → `agent.test.ts` asserts the shape of the object returned by `#options()` (or an equivalent exposed test seam) for both a set and an unset model; AC #3 → `session.test.ts` asserts (via a mock/spy on `ReviewAgent`'s constructor or its resulting `Options`) that the right model reaches the right chat's agent; AC #4 → a test exercising a model change followed by a message, asserting the documented behavior; AC #5 → existing pass-related tests remain green.
- **Fixtures / mocks:** mock the SDK's `query` function (already necessary for `agent.test.ts` to avoid real API calls) and inspect the `Options` object it was called with.
- **Edge cases to cover:** empty-string model (`""`) should behave like `null` (omitted), not be passed through as a literal empty string to the SDK.
