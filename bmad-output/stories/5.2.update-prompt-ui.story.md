# 5.2: Web `UpdatePrompt.tsx`: button → modal → copy-to-clipboard

**Story ID:** 5.2
**Epic:** 5 — Update Checks
**Slug:** update-prompt-ui
**Status:** ready-for-dev

## Story

As a **reviewer**,
I want **to see, inside the review UI I already use daily, that a newer ReviewGate release exists, and get the exact update command with one click**,
so that **I can act on an available update without leaving the browser or remembering the CLI command myself**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A new `UpdatePrompt` component calls `GET /api/update-check` exactly once per full page load (on mount), and does not poll, re-call on every `App.tsx` re-render, or re-call when the review's state changes via SSE.
2. While the check has not yet resolved, or resolves with `updateAvailable: false`, the component renders nothing — no placeholder, spinner, or layout shift/flash is visible.
3. When the check resolves with `updateAvailable: true`, a clearly visible button/badge appears in the app header; clicking it opens a modal.
4. The modal displays the exact literal command `reviewgate update` (e.g. in a monospace/code element) and a copy-to-clipboard control next to it; activating the copy control places the exact string `reviewgate update` on the system clipboard.
5. A failed check (network error, non-OK response, thrown exception, or an unparseable response body) is caught and swallowed silently — no error message or crash is visible to the reviewer, and no button/badge renders for that page load.
6. `UpdatePrompt` is mounted exactly once, from `packages/web/src/App.tsx`'s header block (the same region already holding the panel/view toggle button groups) — not from the `decision != null` branch — so it occupies a disjoint region of `App.tsx` from Story 4.1's final-page branding change.

## Tasks / Subtasks

- [ ] Add a standalone `fetchUpdateCheck(): Promise<UpdateCheckResult>` export to `packages/web/src/lib/reviewClient.ts` that calls `fetch("/api/update-check")` directly (no `ctx`/token, unlike every other export in that file) and returns the parsed JSON typed as `UpdateCheckResult` from `@reviewgate/core/api` (AC: #1)
- [ ] Create `packages/web/src/components/UpdatePrompt.tsx`: on mount (`useEffect` with an empty dependency array), call `fetchUpdateCheck()`, store the result (or "not yet resolved"/"failed") in local state, and wrap the call in a `try/catch` that swallows any error into the "no button" state (AC: #1, #2, #5)
- [ ] Render `null` whenever state is "not yet resolved," "failed," or `updateAvailable: false`; render a small button/badge only when `updateAvailable: true` (AC: #2, #3)
- [ ] Add local `isModalOpen` state to `UpdatePrompt.tsx`; clicking the button/badge opens the modal (AC: #3)
- [ ] Build the modal's markup: an overlay/dialog containing the literal text `reviewgate update` in a `<code className="rg-code">`-style element, a copy button, and a way to close the modal (e.g. an explicit close button, `Escape` key, and/or backdrop click) (AC: #3, #4)
- [ ] Wire the copy button to `navigator.clipboard.writeText("reviewgate update")`; guard the call (feature-detect `navigator.clipboard`, catch a rejected promise) so an unsupported/blocked clipboard API does not throw or crash the modal (AC: #4)
- [ ] Add the minimal CSS this modal needs to `packages/web/src/styles.css` (no existing modal/overlay class exists in this codebase to reuse) (AC: #3, #4)
- [ ] Mount `<UpdatePrompt />` inside the `ml-auto flex items-center gap-2` container in `App.tsx`'s `<header>` block, alongside the existing panel-tab and view-toggle button groups, passing no props (AC: #6)
- [ ] Manually verify in a browser against a running server: no update available → nothing renders; update available (e.g. by forcing the server's cached verdict) → button appears, modal opens, copy places the exact command on the clipboard (AC: #1-#6)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Requirement:** FR-008 — "When an update is available, a clearly-visible button/badge appears; clicking it opens a modal showing the exact update command (`reviewgate update`) and a copy-to-clipboard button next to it. When already up to date, or the check has not yet run today and hasn't completed, no button is shown (no false positives, no layout flash). A failed check... is silent to the reviewer... and does not retry more than once per day." [Source: tech-spec.md#fr-008-daily-cached-update-check-with-an-in-app-prompt-must]
- **Key Component contract:** "Call the update-check endpoint once per page load; render nothing when no update is available or the check hasn't resolved yet. When available, render a small button/badge; clicking opens a modal with the `reviewgate update` command in a code block and a copy-to-clipboard button." New component, e.g. `UpdatePrompt.tsx`, "mounted once near `App.tsx`'s header." [Source: tech-spec.md#update-prompt-ui-round-2--new-component-in-packageswebsrccomponents]
- **The contract Story 5.1 establishes, which this story consumes as-is (not yet built at authoring time, but locked by 5.1's Acceptance Criteria):**
  - `GET /api/update-check` returns `{ current: string; latest: string | null; updateAvailable: boolean }`, typed as `UpdateCheckResult` and exported from `@reviewgate/core/api` — import that type rather than redeclaring the shape locally.
  - The endpoint requires no review id and no bearer token (unlike every `/api/review/:id/...` route) — it is reachable as a bare, unauthenticated `fetch("/api/update-check")`, the same way the browser could call `/healthz`. Do not route this call through `reviewClient.ts`'s `send()`/`createReviewApi` helpers or `api.ts`'s `get()` helper — both of those are hard-coded to `/api/review/${ctx.id}${path}` with an `authorization` header, which this endpoint neither needs nor expects.
  - The server already rate-limits itself to one GitHub call per calendar day and caches failures too — the web layer must not try to retry, poll, or work around a `false`/failed result; one fetch per page load is both necessary and sufficient.
  [Source: bmad-output/stories/5.1.update-check-endpoint.story.md]
- **Mount point, read directly from `packages/web/src/App.tsx` (lines 255-308):** the header's `ml-auto flex items-center gap-2` `<div>` currently holds two button-group `<div role="group">` blocks (the "chat/comments" panel toggle and the "unified/split" view toggle). This is the natural, lowest-risk place to add a third sibling element for the update prompt — same visual row, same right-aligned cluster, no restructuring of the surrounding layout. This region is only reached once `ctx`, `summary`, `review`, and `api` are all resolved and `decision == null` (every earlier `return` in the component — no-context, error, loading, decision-made — happens before this JSX is reached), so `UpdatePrompt` is not visible on those screens; this is acceptable because a reviewer who is not yet looking at a live diff has nothing to act on yet, and matches the tech spec's framing of "a reviewer already looking at the review UI." [Source: packages/web/src/App.tsx]
- **Same-file overlap with Story 4.1, called out explicitly in both `epics.md` and Story 4.1's own Owned File/Module Scope:** Story 4.1 changes the `decision != null` branch's `<Centered>` block (lines ~206-218); this story changes the header's `ml-auto` div (lines ~255-308). These are disjoint regions of the same file and are not schedulable in the same parallel wave under the file-level scope-conflict rule, even though they do not semantically collide — merge sequentially. [Source: bmad-output/epics.md#epic-5-update-checks]; [Source: bmad-output/stories/4.1.final-page-logo.story.md]
- **No existing modal/dialog/overlay component or CSS class exists anywhere in `packages/web/src`** (confirmed: no `role="dialog"`, no "Modal", no overlay/backdrop CSS class in `styles.css`) — this story is the first to need one, and there is nothing to reuse. Keep it minimal: a fixed-position overlay plus a centered panel is sufficient; do not build a general-purpose reusable `<Modal>` abstraction beyond what this one use needs, since no other in-scope story asks for one. [Inference]
- **No existing clipboard-copy code exists anywhere in `packages/web/src`** — this is new. Use the standard `navigator.clipboard.writeText(...)` API (available in all browsers this project already targets, per the existing use of `EventSource`/other modern browser APIs elsewhere in `packages/web`), and fail silently (no thrown error surfaced to the reviewer) if it is unavailable or rejects, consistent with the project's "never block/alarm the reviewer over a non-critical failure" posture already established for the check itself. [Inference]
- **`rg-code` styling already exists** for monospace/code text (`font-family: var(--rg-font-code); font-size: var(--rg-size-code); line-height: var(--rg-line-code); tab-size: 2;`), already used for an inline command example in `App.tsx`'s "Not a valid review URL" message (`<code className="rg-code">reviewgate open</code>`) — reuse this class for the `reviewgate update` command text in the modal rather than inventing new command-text styling. [Source: packages/web/src/styles.css]; [Source: packages/web/src/App.tsx]
- **"Once per page load," not "once per component mount that could recur":** because `UpdatePrompt` is mounted once, statically, inside `App.tsx`'s JSX (not conditionally re-mounted as other state changes), a `useEffect` with an empty dependency array fires exactly once for the component's lifetime on that page, which is the correct implementation of "once per page load" — no additional guard (e.g. a ref or session-storage flag) is needed. [Inference]
- **Never blocks or gates anything:** this is a read-only, informational surface — it must never affect `openComments()`, the Approve/Request-changes gate, or any other review state, and must not be awaited by anything else in `App.tsx`'s render path (fire-and-forget fetch inside its own effect, isolated from `summary`/`review` state). [Source: tech-spec.md#constraints]
- **Out of scope reminders:** no auto-install — the modal only ever shows the command to run manually, it never executes it; no change to any other part of the header, the panel toggles, or the view toggles. [Source: bmad-output/epics.md#epic-5-update-checks]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Approach:** this codebase has no React component test harness in `packages/web` (no jsdom/testing-library dependency, no `*.test.tsx` files) — this conclusion was already reached and documented in Story 1.4's Dev Agent Record, and holds here too. Verify via: (1) `npx tsc --noEmit` on `packages/web` staying clean, (2) `npm run build:web` (a real Vite production build) succeeding, (3) the full `npm test` suite showing no regressions, and (4) a manual browser pass against a running server (mirroring Story 4.1's and 1.4's testing approach for UI-only stories in this codebase). [Source: bmad-output/stories/1.4.chat-switcher-ui.story.md]
- **Key scenarios:**
  - Mock/stub `fetchUpdateCheck()` (or the underlying `fetch`) to resolve `{ current: "v0.2.0", latest: null, updateAvailable: false }` and confirm nothing renders (AC #2).
  - Mock it to resolve `{ current: "v0.2.0", latest: "v0.3.0", updateAvailable: true }` and confirm the button/badge appears, clicking it opens the modal, the modal shows the literal text `reviewgate update`, and clicking the copy control results in `navigator.clipboard.writeText` being called with exactly `"reviewgate update"` (AC #3, #4).
  - Mock it to reject (network error) or resolve a malformed body and confirm no button renders and nothing throws to the console in a way that surfaces to the reviewer (AC #5).
  - Confirm the fetch happens exactly once across a sequence of unrelated `App.tsx` state changes (e.g. simulate an SSE `onReview` update, a view toggle, a panel toggle) — the mocked fetch's call count should stay at 1 (AC #1).
  - Visual/manual check against a live server: force the server's cache file (from Story 5.1) to report an available update, load the page, confirm the button/modal/copy flow end to end with a real clipboard write; then force it to report up to date and confirm nothing renders (AC #1-#6).
  - Manual check that the mount point sits in the header's toggle-button row and that Story 4.1's decision-branch content (once implemented) is unaffected by this change and vice versa (AC #6).
- **Fixtures/mocks:** since there is no component test harness, "mocking" here means either (a) a small manual/local harness the dev agent writes ad hoc to exercise the component in isolation if one is set up as part of this story, or (b) hand-tracing the code against each scenario plus the manual browser pass — follow whichever approach Story 1.4 documents as the precedent (hand-tracing + manual pass) unless a test harness is added as an explicit, separately-scoped effort. Do not introduce a new testing framework/dependency as an implicit side effect of this story.
- **Edge cases to cover:** `navigator.clipboard` unavailable (e.g. non-secure/`http://` context, though ReviewGate is always served from `127.0.0.1` which browsers treat as a secure context — confirm the copy control does not throw regardless) or the clipboard write promise rejecting (e.g. permission denied) — the modal must remain usable and not crash; a very long or unexpected `latest` version string should not break the button/badge layout; opening and closing the modal repeatedly should not leak event listeners (e.g. an `Escape`-key handler added on open must be removed on close/unmount).

## Learnings from Previous Stories

- The contract 5.1 establishes (not yet `done`, but locked by its own Acceptance Criteria at the time this story was authored): `GET /api/update-check` → `{ current, latest, updateAvailable }` typed as `UpdateCheckResult` in `@reviewgate/core/api`; the route is unauthenticated and not review-scoped; a failed or not-yet-run check is indistinguishable from "no update" at the response level (`updateAvailable: false`), so this story does not need its own retry/backoff logic — the server already owns that (from 5.1).
- From 1.4 (`chat-switcher-ui`, Dev Agent Record): this codebase has no React component test harness — plan for hand-tracing + a manual browser pass rather than assuming component tests can be written, and verify with `tsc --noEmit` / `npm run build:web` / the full `npm test` suite instead.
- From 4.1 (`final-page-logo`, Dev Notes): the same "no existing precedent, build the minimal thing this one use needs" reasoning 4.1 applied to theme-CSS applies here to the modal/overlay CSS — do not over-build a reusable abstraction beyond what `UpdatePrompt` itself needs.
