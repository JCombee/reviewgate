# 2.2: Model picker UI bound to the active chat

**Story ID:** 2.2
**Epic:** 2 — Per-Chat Model
**Slug:** model-picker-ui
**Status:** ready-for-dev

## Story

As a **reviewer**,
I want **a simple control in the chat panel to pick which model answers the active chat**,
so that **I can choose a faster or stronger model per conversation without leaving the review**.

## Acceptance Criteria

1. `ChatPanel.tsx` renders a model `<select>` (or equivalent) for the active chat, offering "Default" plus a small fixed list of known aliases (`sonnet`, `opus`, `fable`, `haiku`).
2. The picker's value reflects the active chat's current `model` (`null` → "Default").
3. Changing the picker's value calls a new `ReviewApi.setChatModel(chatId, model)` (added in this story, following the existing `run()` pattern in `reviewClient.ts`) which `PATCH`es `/api/review/:id/chats/:chatId` and updates the review from the response.
4. The picker only ever sends one of the fixed known values (or omits/`null`s the field for "Default") — it must not accept or forward arbitrary free-text input to the server.
5. `packages/server/src/app.ts` gains the `PATCH /api/review/:id/chats/:chatId` route (`{ model?: string | null }` body) wired to a small `Session.setChatModel(chatId, model)` method that updates the matching `Chat.model` and persists via `commit()`.

## Tasks / Subtasks

- [ ] Add `Session.setChatModel(chatId, model)` — updates `Chat.model` for the matching chat, replaces the cached `ReviewAgent` for that chat id (per Story 2.1's documented model-change behavior), and `commit()`s (AC: #5)
- [ ] Add `PATCH /api/review/:id/chats/:chatId` route in `app.ts` calling `Session.setChatModel` (AC: #5)
- [ ] Add `ReviewApi.setChatModel(chatId, model)` in `reviewClient.ts` (AC: #3)
- [ ] Add the model `<select>` to `ChatPanel.tsx`'s chat switcher header (from Story 1.4), bound to `activeChat.model`, with a fixed `<option>` list (AC: #1, #2)
- [ ] Ensure the `<select>`'s `onChange` only ever passes through one of the fixed values (native `<select>` already guarantees this; do not wire a free-text fallback) (AC: #4)
- [ ] Wire "New chat" (Story 1.4) to optionally pass an initial `model` through `createChat(title?, model?)` if the picker's current default selection should carry over to new chats (nice-to-have; do not block the story on this)

## Dev Notes

- The fixed alias list mirrors the tech-spec's explicit choice not to query the SDK for a live model list, keeping the security surface small (only known-good values ever reach `Options.model`). [Source: tech-spec.md#nfr-security, tech-spec.md#decisions-log-summary]
- `Session.setChatModel` should follow the same shape as `Session.decide`/`Session.chat` (read `#review`, produce a new `Review` value, call `this.commit(next)`) rather than mutating `#review` in place — every other mutation in `session.ts` follows this immutable-update-then-commit pattern. [Source: packages/server/src/session.ts]
- Recreating the cached `ReviewAgent` for a chat id on model change was the behavior chosen in Story 2.1 (AC #4) — `setChatModel` should evict that chat's entry from the `#agents` map (from Story 1.2) so the next message lazily reconstructs it with the new model. [Source: bmad-output/stories/2.1.agent-model-option.story.md]
- Follow `app.ts`'s existing `mutate()` helper convention for the new `PATCH` route (see e.g. the `PUT /commit-message` route at `app.ts:227-233`, which is the closest existing precedent for a small single-field update route). [Source: packages/server/src/app.ts]
- Place the picker in the same header row as the chat switcher (Story 1.4) rather than as a separate panel section — it is a property of "the active chat", same visual tier as the chat's title. [Inference]

## Testing

- **Approach:** server-side route/unit tests (`app.test.ts`, `session.test.ts`) plus a manual browser check for the picker itself.
- **Key scenarios:** setting a chat's model via the API updates `Chat.model` and the next message to that chat uses it (verified by inspecting the `Options` passed to the mocked SDK `query`, per Story 2.1's test seam); the UI picker only ever offers/sends the fixed alias list; switching the picker back to "Default" sends `null` and the next message omits `model` entirely.
- **Per-AC verification:** AC #1/#2 → manual/component check that the select shows the right current value per active chat; AC #3 → test that changing the picker calls the API with the right chatId/model and the review updates; AC #4 → code review / type-level guarantee (no free-text input path exists); AC #5 → `app.test.ct` route test for the new `PATCH` endpoint.
- **Fixtures / mocks:** reuse the mocked SDK `query` from Story 2.1's tests to assert the model actually reaches `Options`.
- **Edge cases to cover:** setting a chat's model back to "Default" (`null`) after it was previously set to a specific alias; setting a model on a chat that already has messages (existing history must not be lost or altered, only future messages are affected).
