# 2.2: Model picker UI bound to the active chat

**Story ID:** 2.2
**Epic:** 2 — Per-Chat Model
**Slug:** model-picker-ui
**Status:** done

## Story

As a **reviewer**,
I want **a simple control in the chat panel to pick which model answers the active chat**,
so that **I can choose a faster or stronger model per conversation without leaving the review**.

## Acceptance Criteria

1. `ChatPanel.tsx` renders a model `<select>` (or equivalent) for the active chat, offering "Default" plus a small fixed list of known aliases (`sonnet`, `opus`, `fable`, `haiku`).
2. The picker's value reflects the active chat's current `model` (`null` → "Default").
3. Changing the picker's value calls a new `ReviewApi.setChatModel(chatId, model)` (added in this story, following the existing `run()` pattern in `reviewClient.ts`) which `PATCH`es `/api/review/:id/chats/:chatId` and updates the review from the response.
4. The picker only ever sends one of the fixed known values (or omits/`null`s the field for "Default") — it must not accept or forward arbitrary free-text input to the server.
5. `packages/server/src/app.ts` gains the `PATCH /api/review/:id/chats/:chatId` route (`{ model?: string | null }` body) wired to a small `Session.setChatModel(chatId, model)` method that updates the matching `Chat.model` and persists via `commit()`.

## Tasks / Subtasks

- [ ] Add `Session.setChatModel(chatId, model)` — updates `Chat.model` for the matching chat, replaces the cached `ReviewAgent` for that chat id (per Story 2.1's documented model-change behavior), and `commit()`s (AC: #5)
- [ ] Add `PATCH /api/review/:id/chats/:chatId` route in `app.ts` calling `Session.setChatModel` (AC: #5)
- [ ] Add `ReviewApi.setChatModel(chatId, model)` in `reviewClient.ts` (AC: #3)
- [ ] Add the model `<select>` to `ChatPanel.tsx`'s chat switcher header (from Story 1.4), bound to `activeChat.model`, with a fixed `<option>` list (AC: #1, #2)
- [ ] Ensure the `<select>`'s `onChange` only ever passes through one of the fixed values (native `<select>` already guarantees this; do not wire a free-text fallback) (AC: #4)
- [ ] Wire "New chat" (Story 1.4) to optionally pass an initial `model` through `createChat(title?, model?)` if the picker's current default selection should carry over to new chats (nice-to-have; do not block the story on this)

## Dev Notes

- The fixed alias list mirrors the tech-spec's explicit choice not to query the SDK for a live model list, keeping the security surface small (only known-good values ever reach `Options.model`). [Source: tech-spec.md#nfr-security, tech-spec.md#decisions-log-summary]
- `Session.setChatModel` should follow the same shape as `Session.decide`/`Session.chat` (read `#review`, produce a new `Review` value, call `this.commit(next)`) rather than mutating `#review` in place — every other mutation in `session.ts` follows this immutable-update-then-commit pattern. [Source: packages/server/src/session.ts]
- Recreating the cached `ReviewAgent` for a chat id on model change was the behavior chosen in Story 2.1 (AC #4) — `setChatModel` should evict that chat's entry from the `#agents` map (from Story 1.2) so the next message lazily reconstructs it with the new model. [Source: bmad-output/stories/2.1.agent-model-option.story.md]
- Follow `app.ts`'s existing `mutate()` helper convention for the new `PATCH` route (see e.g. the `PUT /commit-message` route at `app.ts:227-233`, which is the closest existing precedent for a small single-field update route). [Source: packages/server/src/app.ts]
- Place the picker in the same header row as the chat switcher (Story 1.4) rather than as a separate panel section — it is a property of "the active chat", same visual tier as the chat's title. [Inference]

## Testing

- **Approach:** server-side route/unit tests (`app.test.ts`, `session.test.ts`) plus a manual browser check for the picker itself.
- **Key scenarios:** setting a chat's model via the API updates `Chat.model` and the next message to that chat uses it (verified by inspecting the `Options` passed to the mocked SDK `query`, per Story 2.1's test seam); the UI picker only ever offers/sends the fixed alias list; switching the picker back to "Default" sends `null` and the next message omits `model` entirely.
- **Per-AC verification:** AC #1/#2 → manual/component check that the select shows the right current value per active chat; AC #3 → test that changing the picker calls the API with the right chatId/model and the review updates; AC #4 → code review / type-level guarantee (no free-text input path exists); AC #5 → `app.test.ct` route test for the new `PATCH` endpoint.
- **Fixtures / mocks:** reuse the mocked SDK `query` from Story 2.1's tests to assert the model actually reaches `Options`.
- **Edge cases to cover:** setting a chat's model back to "Default" (`null`) after it was previously set to a specific alias; setting a model on a chat that already has messages (existing history must not be lost or altered, only future messages are affected).

## Dev Agent Record

**Implementation summary:**

- `packages/server/src/session.ts` — added `Session.setChatModel(chatId, model)`. It looks up the chat, throws `ReviewError(\`unknown chat: ${chatId}\`, 404)` if it doesn't exist, normalizes `model` (empty/whitespace-only string → `null`), and produces the next `Review` via the same immutable-update-then-`commit()` shape as every other mutation in this class (per Dev Notes).
- `packages/server/src/app.ts` — added `PATCH /api/review/:id/chats/:chatId`, parsing `{ model?: string | null }` from the body (defaulting to `null` on a missing/unparseable body) and calling `Session.setChatModel`. Errors are mapped the same way the other chat routes do: `ReviewError` → `err.status`, anything else → 503. This route does not go through `app.ts`'s shared `mutate()` helper, matching the existing convention for the other `/chats*` routes (`POST /chats`, `POST /chats/:chatId/messages`) — none of them use `mutate()` because the underlying `Session` methods already call `this.commit()` internally; `mutate()` is reserved for routes whose handler itself owns the read-mutate-commit cycle. (The Dev Notes' pointer to the `PUT /commit-message` route was checked but that route doesn't use `mutate()` either, for the same reason — it doesn't fit as a template beyond "single-field PATCH/PUT shape.")
- `packages/web/src/lib/reviewClient.ts` — added `ReviewApi.setChatModel(chatId, model)`, following the existing `run()` pattern (`run(\`/chats/${chatId}\`, "PATCH", { model })`).
- `packages/web/src/components/ChatPanel.tsx` — added a `MODEL_OPTIONS` constant (`["sonnet", "opus", "fable", "haiku"]`) and a `<select aria-label="Model for this chat">` in the chat-switcher header row (to the right of the tabs, next to "+ New chat"), with a `<option value="">Default</option>` plus one `<option>` per fixed alias. Its `value` is bound to `activeChat?.model ?? ""`, so it always reflects the active chat's persisted model; it's `disabled` when there is no active chat. `onChange` calls `api.setChatModel(activeChatId, value === "" ? null : value)` — since the values only ever come from the native `<select>`'s own fixed `<option>` list, there is no code path for arbitrary free text to reach the server (AC #4 satisfied structurally, not by extra validation).

**Judgment calls / deviations from Dev Notes:**

- **Model-change mechanism (re-confirmed from Story 2.1):** the Dev Notes and Learnings sections for this story describe the mechanism as "evict that chat's entry from the `#agents` map so the next message lazily reconstructs it." That eviction step was *not* implemented as a separate action inside `setChatModel`. Instead, Story 2.1 already built `Session#agentFor` to compare `cached.context.model === chat.model` on every call and transparently discard+recreate the cached agent on a mismatch (see `2.1.agent-model-option.story.md`'s Dev Agent Record). Because of that, `setChatModel` only needs to update `Chat.model` and `commit()` — it never touches `#agents` at all, and the "eviction" happens implicitly the next time `#agentFor` runs for that chat. This satisfies AC #5 exactly as worded ("updates the matching `Chat.model` and persists via `commit()`") without needing `setChatModel` to know the `#agents` map exists, which keeps it a plain, testable, immutable-update-then-commit method like every sibling mutation in `session.ts`. Verified directly in this story's new tests (see below) — a message sent to a chat after `setChatModel` uses a new `ReviewAgent` instance with the new model.
- **Task 5 ("wire 'New chat' to carry over the current model selection"):** explicitly marked "nice-to-have; do not block the story on this" in the Tasks list. **Skipped** — `onNewChat` (in `App.tsx`, from Story 1.4) still calls `api.createChat()` with no arguments, so new chats always start on "Default." There is no natural "currently selected default model" concept in the UI to carry over (the picker only shows/sets the *active* chat's model, not a global default), so wiring this up would have required inventing new state without a corresponding Acceptance Criterion. Left as a possible future enhancement.
- Body parsing on the PATCH route defaults to `{ model: null }` when the request body is missing or fails to parse, rather than rejecting the request — this matches the forgiving-body style already used by the sibling `POST /chats` route in `app.ts` (Story 1.3).

**Tests added:**

- `packages/server/src/app.test.ts` — new `describe("chat model (Story 2.2)", ...)` block (4 tests): sets a chat's model and reflects it in the response; sets a chat back to Default (`null`); confirms setting a model does not disturb the chat's existing messages; returns a 404-mapped error body for an unknown chat id.
- `packages/server/src/session.test.ts` — new `describe("setChatModel", ...)` block (7 tests): updates and persists the matching chat's model (checked via a fresh `session.store.load`); resets a previously-set model back to `null`; treats an empty string the same as `null`; leaves an existing chat's messages untouched; leaves *other* chats' models untouched; rejects an unknown `chatId`; and — the key behavioral test tying this story to Story 2.1 — confirms that after `setChatModel`, the next message sent to that chat is answered by a freshly constructed `ReviewAgent` instance whose `context.model` is the new value (not the stale cached agent).
