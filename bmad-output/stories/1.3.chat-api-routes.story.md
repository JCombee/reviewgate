# 1.3: Chat-id-aware API routes + SSE `chatId` tagging

**Story ID:** 1.3
**Epic:** 1 — Multiple Chats
**Slug:** chat-api-routes
**Status:** ready-for-dev

## Story

As a **web client**,
I want **HTTP routes and SSE events that identify which chat a message or token belongs to**,
so that **the browser can route streamed answers and history to the right chat thread instead of assuming there is only one**.

## Acceptance Criteria

1. `POST /api/review/:id/chat` (`packages/server/src/app.ts`) is replaced with `POST /api/review/:id/chats/:chatId/messages`, which validates `{ message: string }` exactly as today and calls `Session.chat(chatId, message)`.
2. A new `POST /api/review/:id/chats` route accepts an optional `{ title?, model? }` body, calls `Session.createChat(title, model)`, and returns the updated `Review`.
3. The `chat-token` SSE event (`packages/core/src/api.ts`'s `ReviewEvent` union) gains a required `chatId: string` field; `Session`'s emission of that event (`session.ts`) includes the chat id the token belongs to.
4. `packages/web/src/lib/reviewClient.ts`'s `ReviewApi.chat` becomes `chat: (chatId: string, message: string) => Promise<void>`, and a new `createChat: (title?: string, model?: string | null) => Promise<void>` is added; `subscribeToReview`'s `onChatToken` handler signature becomes `(chatId: string, text: string) => void`.
5. Existing non-chat routes and their tests in `app.ts`/`app.test.ts` are unaffected.

## Dev Notes

- Current route: `app.post("/api/review/:id/chat", ...)` validates `body?.message` is a non-empty string, calls `s.chat(message)`, returns `{ review }` on success or `{ error }` with 503 on `AgentUnavailable`-style failure. [Source: packages/server/src/app.ts:237-251]
- `Session.chat` becomes `chat(chatId, message)` per Story 1.2 — this story only needs to thread `c.req.param("chatId")` into that call; no new error-handling shape is needed beyond what already exists (missing/invalid `chatId` surfaces as the same `503 { error }` path via `Session`'s thrown error, AC #4 of Story 1.2). [Source: bmad-output/stories/1.2.server-chat-map.story.md]
- `ReviewEvent` is defined as a discriminated union `{ type: "review"; review } | { type: "chat-token"; text } | { type: "pass"; status } | { type: "ping" }` in `packages/core/src/api.ts:111-115` — add `chatId: string` only to the `chat-token` member, not the others. [Source: packages/core/src/api.ts]
- `subscribeToReview` (`packages/web/src/lib/reviewClient.ts:80-102`) currently does `else if (event.type === "chat-token") handlers.onChatToken?.(event.text)`; this becomes `handlers.onChatToken?.(event.chatId, event.text)`. The `EventSource` listener registration loop (`for (const name of ["review", "chat-token", "pass"])`) is unaffected — event *names* don't change, only the payload shape. [Source: packages/web/src/lib/reviewClient.ts]
- `ReviewApi.chat` is called from exactly one place today, `ChatPanel.tsx`'s `send()` — that call site is Story 1.4's responsibility to update; this story only changes the `ReviewApi` interface and its `reviewClient.ts` implementation, accepting that `ChatPanel.tsx` will not compile again until Story 1.4 lands (same pattern as Story 1.2 → 1.3). [Inference]
- Keep the response shape `{ review: Review }` identical to every other mutating route in `app.ts` (see `mutate()` helper at `app.ts:134` and its call sites) — do not special-case chat routes' response envelope. [Source: packages/server/src/app.ts]

## Testing

- **Approach:** integration tests in `packages/server/src/app.test.ts`, following its existing pattern of exercising routes through the Hono app instance (no real SDK calls — `Session`'s agent calls should already be mockable per Story 1.2's test setup).
- **Key scenarios:** `POST /chats` creates a chat and it appears in the returned `Review.chats`; `POST /chats/:chatId/messages` on a valid chat id appends messages and streams a `chat-token` event carrying that `chatId`; the same route on an unknown `chatId` returns an error response (503, matching the existing `AgentUnavailable` convention) rather than a 500 or silent success.
- **Per-AC verification:** AC #1 → route test posts a message to a created chat and asserts the review reflects it; AC #2 → route test posts to `/chats` and asserts a new `Chat` appears; AC #3 → an SSE-level test (or a unit test on `Session`'s emit call) asserts the emitted event object has `chatId`; AC #4 → `reviewClient.ts` type-checks against the updated `ReviewApi` interface and a unit test (mocking `fetch`/`EventSource`) confirms `chat(chatId, message)` posts to the new path; AC #5 → the full existing `app.test.ts` suite passes unchanged.
- **Fixtures / mocks:** a stub/mock `Session` (or the real `Session` with a stubbed `ReviewAgent`) wired the same way existing `app.test.ts` cases already set up sessions for other routes.
- **Edge cases to cover:** posting a message with `chatId` referring to a chat that was just created in the same test (race-free, since it's sequential); malformed/missing `chatId` path param (Hono routing already guarantees a string here, so this reduces to "unknown id" rather than "wrong type").
