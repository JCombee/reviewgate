# 6.1: Run `pre-commit` before diff capture; deny early on failure

**Story ID:** 6.1
**Epic:** 6 — Hook Ordering
**Slug:** precommit-hook-runner
**Status:** ready-for-dev

## Story

As the **PreToolUse gate that intercepts every `git commit`**,
I want **to run the repo's own `pre-commit` hook, resolved the same way git resolves it, before capturing the diff for review**,
so that **a commit that is going to fail its own hooks is denied before a human spends time reviewing it, and a diff a human approves reflects whatever the hook itself rewrote**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A new hook-runner resolves the hooks directory via `git config --get core.hooksPath` (a relative value is resolved against the repo root), falling back to `<gitDir>/hooks` when `core.hooksPath` is unset; a missing or non-executable `pre-commit` file at that location is treated the same as "no hook" and does not change `decide()`'s behavior.
2. When an executable `pre-commit` file exists there, `decide()` (`packages/cli/src/commands/hook.ts`) runs it — cwd at the repo root, current process environment — after the `--no-verify` and in-merge-or-rebase checks, and before `git.rawDiff(analysis.scope, options)` is called, for every commit scope (`staged`, `working`, `amend`) `analyzeCommand` can produce.
3. If the hook exits non-zero, `decide()` returns a `{ kind: "deny", reason }` verdict — the same shape `hook.ts` already returns for the `--no-verify` denial — carrying the hook's own combined stdout+stderr as the reason, and no review server/session/browser is started for that invocation.
4. If the hook exits zero, or no hook is present/executable, `decide()` proceeds exactly as it does today: config loads, `git.rawDiff(...)` runs next and captures whatever is on disk at that moment (including anything the hook itself rewrote).
5. Any failure in resolving the hooks directory or spawning the hook (as distinct from the hook's own non-zero exit) is treated identically to "no hook present" — `decide()` proceeds to the diff/review flow unchanged, and the commit is never denied because the hook-runner itself broke.
6. A repo with no `pre-commit` hook configured (empty/template-only `.git/hooks`, `core.hooksPath` unset) shows no new delay and no new prompt versus `decide()`'s behavior before this story.

## Tasks / Subtasks

- [ ] Create `packages/core/src/hook/precommit.ts` exporting `resolveHooksDir(root, gitDir)` (git-config lookup + fallback) and `runPreCommitHook(root, gitDir)` returning a `PreCommitOutcome` (`{ kind: "none" }` / `{ kind: "pass" }` / `{ kind: "fail"; output }`) (AC: #1, #5)
  - [ ] `resolveHooksDir`: run `git config --get core.hooksPath` (exit code 1 = unset, not an error); resolve a relative result against `root`; default to `path.join(gitDir, "hooks")` (AC: #1)
  - [ ] Executable check: POSIX (`darwin`/`linux`, including WSL) uses `fs.access(hookPath, fs.constants.X_OK)`; Windows treats file-exists as sufficient, matching how Git for Windows launches hook scripts without a POSIX exec bit (AC: #1)
  - [ ] Wrap the whole resolve+spawn path in a single try/catch inside `runPreCommitHook` that returns `{ kind: "none" }` on any error not attributable to the hook's own exit code, so this function never throws (AC: #5)
- [ ] Run the resolved hook as a child process (no shell, matching `runGit`'s `execFile`/`shell:false` pattern) with cwd = `root`, capturing stdout+stderr and the exit code (AC: #2, #3)
- [ ] Export `runPreCommitHook` (and `PreCommitOutcome`) from `packages/core/src/index.ts` alongside the other `./hook/*` exports (AC: #2)
- [ ] Wire the call into `decide()` in `packages/cli/src/commands/hook.ts`: call `runPreCommitHook(info.root, info.gitDir)` right after the `info.inMergeOrRebase` check and before `loadConfig`/`git.rawDiff`; on `{ kind: "fail" }` return a `deny` verdict with the hook's `output` as `reason` (falling back to a short generic message if `output` is empty); on `{ kind: "none" }`/`{ kind: "pass" }` fall through unchanged (AC: #2, #3, #4, #5, #6)
- [ ] Add unit tests in `packages/core/src/hook/precommit.test.ts` using `TestRepo`: default (no hook) resolves to `<gitDir>/hooks`; `core.hooksPath` set to a relative path is resolved against the repo root; a non-executable `pre-commit` file is treated as "none"; an executable hook that exits 0 is "pass"; an executable hook that exits non-zero returns "fail" with its output; an unreadable/invalid `core.hooksPath` value does not throw (AC: #1, #4, #5)
- [ ] Extend `packages/cli/src/hook.test.ts` with end-to-end cases: a failing `pre-commit` hook denies the commit before any server/review starts; a `pre-commit` hook that rewrites a staged file results in a review diff reflecting the rewrite; a repo with no hook behaves exactly as the existing suite already asserts (regression) (AC: #2, #3, #4, #6)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Where this lands in `decide()`:** today `decide()` checks `analysis.noVerify` (deny), then `info.inMergeOrRebase` (let through), then `loadConfig`, then `git.rawDiff(analysis.scope, options)` (`packages/cli/src/commands/hook.ts:99-119`, read directly). The new hook run belongs immediately after the `inMergeOrRebase` check and before `loadConfig`/`git.rawDiff`, so a hook that rewrites tracked/staged files is captured by the very next `rawDiff` call with no extra plumbing needed for AC #4 — this ordering is what makes "the diff reflects the post-hook state" true for free, without a separate diff-recapture step. [Source: tech-spec.md#fr-009-run-local-git-hooks-before-opening-the-review-ui-must]
- **Component contract:** the tech-spec's own Key Component names the target signature `runPreCommitHook(gitDir, cwd, scope): Promise<{ ok: true } | { ok: false; output: string }>`, called from `decide()` "right before the noVerify/merge-or-rebase checks resolve into a diff fetch." This story adapts that to a three-way `PreCommitOutcome` (`none`/`pass`/`fail`) instead of a two-way `ok` boolean, so "no hook found" and "hook passed" — both of which must fall through identically — are distinguishable from a genuine failure without the caller re-deriving that distinction; `scope` is not threaded into the resolve/execute path because hook resolution and cwd do not vary by scope, only which git-diff strategy the caller uses after the hook returns. [Source: tech-spec.md#pre-commit-hook-runner-round-2--packagesclisrccommandshookts-packagescoresrchook] [Inference]
- **`core.hooksPath` resolution:** `git config --get core.hooksPath` exits 1 (not an error) when the key is unset — mirror the `okCodes: [0, 1]` pattern `NodeGitClient` already uses for other "may legitimately not exist" git-config/rev-parse calls (e.g. its `HEAD`/branch lookups). A relative `core.hooksPath` value (the shape Husky's `core.hooksPath .husky` convention produces) is resolved against the repo root, not the git dir, matching how the value is meant to point at a directory tracked inside the working tree. [Source: tech-spec.md#fr-009-run-local-git-hooks-before-opening-the-review-ui-must] [Inference]
- **Reuse the existing git-invocation pattern, don't hand-roll a new one:** the tech-spec's own risk mitigation for cross-platform `core.hooksPath` resolution says to "reuse `NodeGitClient`'s existing cross-platform git invocation instead of hand-rolling path logic" — concretely this means using `runGit`'s `execFile`-with-`shell:false` pattern (`packages/core/src/git/exec.ts`) as the template for resolving the config value and for spawning the hook file itself, rather than composing a shell string. [Source: tech-spec.md#risks--mitigations] [Inference]
- **Executable detection differs by platform, and this is the primary named risk:** the Round 2 risk table calls out `core.hooksPath` resolution differing across macOS/Linux/Windows/WSL specifically for "path separators, executable bit, shebang handling," and asks for a test per platform path shape, not just Unix. This story's approach: POSIX platforms (`darwin`, `linux` — WSL's Node process reports `linux`) require the POSIX executable bit (`fs.constants.X_OK`); Windows has no POSIX exec-bit concept and Git for Windows launches hook scripts (typically shebang'd shell scripts) through its own bundled shell regardless of a chmod state, so on `win32` this story treats file-existence as sufficient. Full replication of git's own shebang-interpreter selection on Windows is explicitly out of scope for this story — a `pre-commit` file that exists on Windows but isn't actually runnable by the platform's shell will surface as a spawn failure, which AC #5 requires to fail open (treated as "none"), not as a denial. [Source: tech-spec.md#risks--mitigations] [Inference]
- **Fail-open is the load-bearing constraint, and it is narrower than "abort the whole hook":** Constraint #4 requires that "a broken/missing `pre-commit` hook, or a hook runner failure unrelated to the hook's own logic (e.g. cannot resolve `core.hooksPath`), must fail open (let the commit proceed to review) rather than block." Proceeding *to review* — not skipping review — is the key distinction: `runPreCommitHook` must swallow its own resolution/spawn errors internally and return `{ kind: "none" }` rather than throwing, so `decide()` falls through to the normal `loadConfig`/`git.rawDiff`/review-session path exactly as if no hook existed. Letting such an error propagate up to `runHook()`'s existing top-level try/catch (`hook.ts:78-80`) would instead abort the entire review for that invocation (empty stdout, exit 0, no verdict emitted) — a stricter, unintended form of "fail open" that this story must not rely on for ordinary hook-runner errors. [Source: tech-spec.md#constraints] [Source: packages/cli/src/commands/hook.ts]
- **The `Verdict` shape to reuse:** `hook.ts` already defines `type Verdict = { kind: "allow"; context?: string } | { kind: "deny"; reason: string }` and constructs a `deny` verdict for `--no-verify` at lines 99-106 with a short, git-flavored explanation string. The new `pre-commit` denial follows the identical shape, differing only in that `reason` is the hook's own captured output (trimmed), not an authored message — falling back to a short generic string (e.g. `` `pre-commit` exited with code ${code}.``) only when the hook produced no output at all. [Source: packages/cli/src/commands/hook.ts]
- **Idempotency is a documented, accepted risk, not something this story mitigates further:** the risk table notes that running `pre-commit` a second time (once here, once when the real `git commit` executes after approval) can surprise a non-idempotent hook, and explicitly scopes this change to `pre-commit` only (not `commit-msg` or other hooks) on the basis that mainstream `pre-commit` tooling (lint-staged, prettier, husky) is already expected to tolerate being re-run. This story does not add any de-duplication/skip-on-second-run logic — that would reintroduce state tracking the tech-spec deliberately avoided. [Source: tech-spec.md#risks--mitigations]
- **Module placement:** the new file lives at `packages/core/src/hook/precommit.ts`, alongside the existing `hook/command.ts` (`analyzeCommand`), `hook/feedback.ts`, and `hook/wait.ts` — the same directory and one-function-per-file convention `packages/core/src/index.ts` already re-exports from (`export { analyzeCommand, ... } from "./hook/command.js";`). [Source: packages/core/src/index.ts]
- **Scope note on "working"/"amend" and staging timing [Inference, flagged limitation]:** the hook intercepts the *entire* Bash tool call before any of its shell segments run (`hook.ts`'s own doc comment: "`git add -A && git commit -m "..."` ... means nothing is staged yet at hook time"). For `scope: "working"`/`"amend"` commands whose staging (`git add -A`, `-a`, or an earlier `git add` segment) has therefore not executed yet, a real `pre-commit` script that inspects the git index (e.g. via `git diff --cached`) may see less staged than the eventual real commit will. This story runs the hook against whatever is on disk/staged at the moment `decide()` calls it — live, not a snapshot — satisfying AC #2's "same working tree state" requirement literally, but does not attempt to synthetically pre-stage files to compensate for this timing gap; that would mutate the repo's index as a side effect of merely reviewing, which is a bigger behavior change than this story's bounded scope. Recorded here so the dev agent does not treat a hook that "passes trivially" on a `working`-scope commit as a bug in this story.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Approach:** unit tests for the pure resolve/execute logic in `packages/core` (vitest, using the existing `TestRepo` helper so tests run against a real throwaway git repo rather than mocked git calls, consistent with `NodeGitClient.test.ts`'s existing style), plus end-to-end tests appended to the existing `packages/cli/src/hook.test.ts`, which already spawns the real CLI binary against a `TestRepo` and inspects its stdout JSON verdict.
- **Key scenarios to prove each AC:**
  - AC #1 — `resolveHooksDir` defaults to `<gitDir>/hooks` when `core.hooksPath` is unset; resolves a relative `core.hooksPath` value against the repo root; a `pre-commit` file present but not executable (POSIX) is treated as no hook.
  - AC #2 — a hook is invoked with cwd at the repo root for each of `staged`, `working`, and `amend` scope commands (three `TestRepo` fixtures, one per scope, each writing a hook that records its own `process.cwd()`/an env marker to a file for the test to assert on).
  - AC #3 — an executable `pre-commit` that exits 1 and writes to stdout/stderr produces a `deny` verdict via the CLI whose `permissionDecisionReason` contains that output, and no `server.json`/review file is ever created for that invocation.
  - AC #4 — an executable `pre-commit` that rewrites a staged file and exits 0 lets the flow proceed; the resulting review's diff (read back via `ReviewStore`) reflects the rewritten content, not the pre-hook content.
  - AC #5 — an unreadable `core.hooksPath` (e.g. pointing at a file, not a directory) or a `pre-commit` "file" that is actually a directory does not throw out of `runPreCommitHook`, and the CLI-level flow proceeds to review exactly as if no hook existed.
  - AC #6 — a `TestRepo` with no hook files at all reaches the existing pre-hook-story behavior of `packages/cli/src/hook.test.ts` unchanged (run the existing "opens a review" scenario after this story's change and confirm it still passes with no new delay/prompt).
- **Fixtures/mocks:** `TestRepo` (already exported from `@reviewgate/core`) for every scenario; hand-written hook scripts written via `TestRepo.write()` plus an explicit `fs.chmod(path, 0o755)` on POSIX (Windows has no equivalent step — note this as a platform-conditional test, matching the Risks table's "test per platform path shape, not just Unix" ask). No network or SDK mocks are needed — this story never touches the review server/agent beyond confirming it is *not* started on denial.
- **Edge cases to cover:** empty `pre-commit` file (exists, executable, but exits 0 with no output — must be "pass", not "fail" on empty output); hook that exits non-zero with empty stdout/stderr (must still deny, using the generic fallback reason); `core.hooksPath` set to an absolute path; `core.hooksPath` set to `.` (repo root itself); a `pre-commit` file present under the resolved directory but named with different casing or a `.sh` extension (must NOT be picked up — git hooks are matched by exact name `pre-commit`, no extension).
