# 4.1: Render the logo + "ReviewGate" name in the final-page block

**Story ID:** 4.1
**Epic:** 4 — Final Page Branding
**Slug:** final-page-logo
**Status:** ready-for-dev

## Story

As a **reviewer**,
I want **to see the ReviewGate mark and name on the page shown after I approve or request changes**,
so that **I have visual confirmation I'm looking at ReviewGate rather than a blank/generic screen**.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. The `decision != null` branch's `<Centered>` block in `App.tsx` renders the ReviewGate logo mark and the "ReviewGate" name above the existing decision status text, for both the `approve` and `request_changes` outcomes.
2. The logo variant shown follows the app's existing light/dark mechanism — `data-theme` attribute override with a `prefers-color-scheme` fallback, matching the `:root:not([data-theme="light"])` / `:root[data-theme="dark"]` pattern already used in `styles.css` — not a single hardcoded SVG reference.
3. The existing status text ("Approved — the commit goes through." / "Changes requested — the feedback is in the session.") and the "You can close this window." copy render unchanged, word-for-word, in their existing colors.
4. No other `<Centered>` call site in `App.tsx` (the "not a valid review URL", "Could not load the review", "loading…", or "No changes in this scope" branches) gains the logo — only the `decision != null` block changes.
5. The correct logo is visible without a page reload when the OS/browser color scheme is toggled (light and dark), with no layout flash or both logos visible simultaneously.

## Tasks / Subtasks

- [ ] Add a small logo element (either two `<img>` tags — one per SVG variant — or a tiny local component) inside the `decision != null` branch's `<Centered>` block in `packages/web/src/App.tsx`, referencing the existing `/logo-dark.svg` and `/logo-light.svg` public assets, each tagged with a distinguishing CSS class hook (AC: #1, #2)
- [ ] Add the "ReviewGate" name as text above the existing status `<span>`, inside the same `<Centered>` block (AC: #1)
- [ ] Add CSS rules to `packages/web/src/styles.css` that show exactly one of the two logo variants at a time, following the same `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) ... }` plus `:root[data-theme="dark"] ...` two-rule pattern already used for `.rg-tok` (AC: #2, #5)
- [ ] Verify no other `Centered` usage in `App.tsx` was touched (AC: #4)
- [ ] Verify the two existing status strings and the "You can close this window." string are byte-for-byte unchanged (AC: #3)
- [ ] Manually toggle the OS/browser color scheme (and, if convenient, set `data-theme="dark"`/`"light"` on `<html>` via devtools) to confirm the correct single logo variant renders in each case with no flash (AC: #2, #5)

- **Exact code to change**, read directly from `packages/web/src/App.tsx` (lines 205-218):
  ```tsx
  const decision = review.rounds[review.rounds.length - 1]?.decision ?? null;
  if (decision != null) {
    return (
      <Centered>
        <span style={{ color: decision === "approve" ? "var(--rg-approve)" : "var(--rg-changes)" }}>
          {decision === "approve"
            ? "Approved — the commit goes through."
            : "Changes requested — the feedback is in the session."}
        </span>
        <br />
        <span className="text-[var(--rg-text-faint)]">You can close this window.</span>
      </Centered>
    );
  }
  ```
  [Source: packages/web/src/App.tsx]
- **`Centered` component** (defined at the bottom of the same file) takes `{ children: ReactNode }` and renders a `<p>` inside a flex-centered `<div>`: `<div className="flex h-full items-center justify-center p-6 text-[var(--rg-text-muted)]"><p>{children}</p></div>`. It is reused by four other call sites in the same file (no-context, error, loading, empty-diff) — those must not be touched by this story (AC #4). [Source: packages/web/src/App.tsx]
- **Theme-switching pattern to reuse**, read directly from `packages/web/src/styles.css` (the existing `.rg-tok` two-color-variant rule, lines 213-226):
  ```css
  .rg-tok { color: var(--rg-tok-l); }
  @media (prefers-color-scheme: dark) {
    :root:not([data-theme="light"]) .rg-tok { color: var(--rg-tok-d); }
  }
  :root[data-theme="dark"] .rg-tok { color: var(--rg-tok-d); }
  ```
  This is the established two-rule shape for "system preference, overridable by an explicit `data-theme` attribute" in this codebase: one rule inside `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-theme="light"])` (system dark, unless explicitly forced light), and one unconditional rule scoped to `:root[data-theme="dark"]` (explicit dark override regardless of system preference). [Source: packages/web/src/styles.css]
- **[Inference]** No code in `packages/web/src` currently sets the `data-theme` attribute on any element (`grep` for `data-theme` in `packages/web/src` matches only the two `styles.css` selector blocks) — it exists today purely as CSS infrastructure for a future manual theme toggle, not yet wired to a UI control. This story does not need to add such a toggle; it only needs its logo markup to respond correctly to the attribute *if and when* something sets it, exactly as the existing color tokens already do.
- **[Inference]** Because CSS `@media (prefers-color-scheme)` queries cannot see element/attribute state, and a `<picture>`/`media`-attribute image swap (the pattern already used for the same two SVGs in the repo's own `README.md`, `<picture><source media="(prefers-color-scheme: dark)" .../></picture>`) only reacts to the OS-level media feature — it would ignore a `data-theme="light"`/`"dark"` override the way the rest of the app's dark-mode-affecting elements do not. The `README.md` `<picture>` approach is therefore not sufficient inside the app itself and should not be copied verbatim; instead, render both logo images (or a single logo with a CSS `content`/`display` swap) as plain `<img>`/`<span>` elements and toggle visibility with the two-rule `.rg-tok`-style CSS selector pair above, so the final page's logo honors the same override affordance as every other themed value in `styles.css`.
- **Assets:** `packages/web/public/logo-dark.svg` and `packages/web/public/logo-light.svg` already exist and are referenced from Vite's `public/` directory at the site root — the existing `<link rel="icon" ... href="/favicon.svg" />` in `packages/web/index.html` confirms the `public/` → `/`-root-path convention this app already uses; the new logo `<img src>`s should follow the same `/logo-dark.svg` / `/logo-light.svg` absolute-path convention. [Source: packages/web/index.html]; [Source: bmad-output/epics.md#epic-4-final-page-branding]
- **Out of scope reminders:** no new logo asset is created; the approve/request-changes status wording and the "you can close this window" wording are not changed, per Epic 4's explicit Out of Scope note. [Source: bmad-output/epics.md#epic-4-final-page-branding]

- **Approach:** this is a small, purely presentational change with no new state, props, or data flow — no unit tests are expected to be added; verify by hand-tracing the rendered JSX/CSS against each Acceptance Criterion, plus a manual browser pass (this codebase has no React component test harness — see prior story `1.4`'s Dev Agent Record for the same conclusion) [Source: bmad-output/stories/1.4.chat-switcher-ui.story.md].
- **Key scenarios:**

  - With the OS/browser set to light mode and no `data-theme` attribute present, confirm only the light-variant logo is visible; repeat with dark mode (AC #2, #5).
  - With the OS/browser set to one scheme and `data-theme` forced to the opposite value (via devtools, setting the attribute on `<html>`), confirm the `data-theme` override wins, mirroring how `.rg-tok`'s colors already behave under the same override (AC #2).
  - Diff the rendered status/"close this window" text against the current production copy to confirm no wording change (AC #3).
  - Visually inspect the other four `Centered(...)` call sites in `App.tsx` (no-context, error, loading, empty-diff) to confirm none of them picked up the logo (AC #4).

- **Edge cases to cover:** rapid OS color-scheme toggling while the final page is already mounted (no flash of both logos or of neither); a browser/OS with no `prefers-color-scheme` support at all (should fall back to whichever variant the unconditional/base CSS rule selects, consistent with how `--rg-tok-l` already behaves as the base case).
